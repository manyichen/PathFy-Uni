# PathFy 全站 p5.js 视觉增强可行性分析

> 版本：1.0  
> 编写日期：2026-08-18  
> 分析范围：除登录/注册白鸟转场外的现有 Web 端页面  
> 目标：在不破坏性能、可访问性和业务效率的前提下，用 p5.js 增强职业规划过程的空间感、生命感和品牌记忆

## 1. 结论摘要

PathFy 当前已经形成“岗位探索 → 材料与画像 → 人岗匹配 → 职业图谱 → 生涯报告 → 月度复盘”的完整业务链路，但多数页面仍以卡片、表格、徽章、ECharts 雷达图和折线图表达结果。它们适合承载精确数据，却难以表现以下三类内容：

1. 数据如何从材料逐渐形成结论；
2. 多个岗位、能力和路径之间的空间关系；
3. 用户行动如何让职业路线持续生长和改变。

p5.js 最适合承担“过程、关系、变化和情绪反馈”，不适合替代按钮、表单、正文、表格或精确图表。因此，全站增强应采用“Canvas 负责感染力，DOM/ECharts 负责解释与操作”的双层结构。

综合业务价值、现有数据成熟度、技术复杂度和性能风险，推荐顺序如下：

| 优先级 | 模块 | 推荐场景 | 综合可行性 | 结论 |
| --- | --- | --- | --- | --- |
| P0 | 职业图谱 | 可交互职业路径星图 | 高 | 最能体现 p5.js 价值，建议首先实施 |
| P1 | 能力画像 | 材料证据汇聚成八维画像 | 高 | 数据成熟，适合一次性生成动画 |
| P1 | 人岗匹配 | 个人能力与岗位要求动态对齐 | 高 | 数据成熟，适合选择岗位时播放 |
| P1 | 性格结果 | 生成式人格指纹 | 中高 | 视觉价值高，但需要补充数值型维度数据 |
| P2 | 生涯报告 | 路径生长、复盘脉冲和调整分叉 | 中高 | 适合局部增强，不应替代报告图表 |
| P2 | 岗位探索 | 岗位星群浏览模式 | 中 | 可作为列表之外的可选探索视图 |
| P3 | 工作流转场 | 证据粒子跨阶段流动 | 中 | 品牌一致性好，但跨路由状态复杂 |
| P3 | 首页 | 用户主动触发的体验画布 | 中低 | 只能延迟加载，不可进入首页初始包 |
| 不建议 | 账户、后台、表格和配置表单 | 常驻 Canvas 动效 | 低 | 会降低效率与可访问性 |

## 2. 当前网站技术与性能边界

### 2.1 当前可视化结构

- 登录/注册页通过 p5.js 实现白鸟飞行和页面转场。
- 能力画像与人岗匹配使用 ECharts 雷达图。
- 生涯报告的发展线使用 ECharts 折线图。
- 首页、工作流阶段条、报告时间轴和大部分业务展示使用 Vue DOM、CSS 和 SVG。
- ECharts 通过 `ChartDeferredMount` 在接近可视区时延迟加载。
- p5.js 当前只在认证页动态加载，离开页面后销毁实例。

这种分层是正确的，后续不应改为“所有页面默认加载 p5”。

### 2.2 当前资源预算

根据 `frontend/.output/bundle-report.json`：

| 指标 | 当前值 | 约束 |
| --- | ---: | ---: |
| 首页初始资源 | 711,507 B / 197,604 B gzip | gzip 不超过 220,000 B |
| p5 认证场景资源组 | 423,817 B / 128,627 B gzip | 仅认证路由加载 |
| ECharts 资源组 | 532,290 B / 181,754 B gzip | 仅图表接近可视区时加载 |
| 基础 JS（排除认证 p5） | 1,494,125 B | 不超过 1,525,000 B |

首页距离 gzip 上限只剩约 22 KB，而 p5 资源组约 129 KB gzip，因此：

- p5.js 不能进入首页初始依赖；
- 新场景必须按路由或用户动作动态导入；
- 同一路由中的多个 p5 场景应复用同一个 p5 核心 chunk；
- 场景自身代码应保持轻量，避免每个页面复制一套粒子引擎；
- 每完成一个阶段必须执行 `pnpm generate` 和 `pnpm bundle:check`。

## 3. p5.js 适用性判断标准

一个区域只有同时满足下列两项以上，才值得引入 p5.js：

1. **关系密度高**：需要同时表达多个节点、路径或群组；
2. **随时间变化**：生成、匹配、复盘或状态迁移本身就是内容；
3. **空间交互明显**：缩放、拖动、悬停、聚类或路径追踪能帮助理解；
4. **情绪价值高**：完成测试、生成画像或形成报告是值得强化的关键时刻；
5. **数据可映射**：颜色、位置、大小和运动能对应真实业务字段，而不是纯装饰。

以下情况不应使用 p5.js：

- 用户需要复制、选择、搜索或编辑文字；
- 内容必须被搜索引擎、读屏器或打印/PDF 准确读取；
- 主要任务是填写表单、比较精确数值或处理后台任务；
- Canvas 只能制造持续运动，但不能增加信息；
- 场景无法为减少动态效果用户提供等价静态视图。

## 4. 统一视觉概念：路径粒子系统

建议不要为每个页面设计互不相关的动效，而是把登录页已经建立的“白鸟、光点、路径和分叉”扩展成统一视觉语言：

```text
材料证据        八维能力        岗位要求        职业路径        月度复盘
  · · ·   →    八向汇聚    →    两侧对齐    →    路线分叉    →    节点脉冲
```

统一语义建议：

| 视觉元素 | 业务含义 |
| --- | --- |
| 微小光点 | 材料、行为或证据 |
| 稳定节点 | 用户、岗位、能力维度或月份 |
| 发光路径 | 能力迁移、匹配关系或行动路线 |
| 路径粗细 | 置信度、权重或证据数量 |
| 路径亮度 | 当前关注度或可行性 |
| 路径分叉 | 多目标选择或计划调整 |
| 脉冲波纹 | 新材料、完成行动或提交复盘 |
| 暖色张力线 | 能力缺口、风险或未完成项 |
| 绿色稳定线 | 优势、已满足要求或已验证行动 |

这样可以让用户在不同页面中自然理解同一套符号，而不是每次重新学习动画含义。

## 5. 各模块详细可行性

### 5.1 职业图谱：可交互职业路径星图

### 当前状态

`frontend/app/pages/graph.vue` 会获取晋升、横向转岗和目标岗位差距数据，`CareerPathView.vue` 主要以路径卡片、阶段列表、徽章和箭头呈现。内容可以阅读，但“图谱”仍然缺乏空间结构，用户难以快速判断：

- 哪些岗位是共同中间节点；
- 哪条路线更短、更稳定；
- 哪些横向岗位与当前岗位高度接近；
- 多条晋升路线在哪里分叉或汇合。

### 推荐场景

新增“图谱视图 / 列表视图”切换，保留现有列表作为精确解释和无障碍回退。

图谱画布中：

- 当前岗位固定为中心主节点；
- 晋升岗位分布在上方；
- 横向岗位分布在左右两侧；
- 目标岗位使用独立高亮环；
- 节点半径映射岗位样本量或资源密度；
- 连线宽度映射路径置信度；
- 连线颜色区分晋升、横向转岗和指定目标迁移；
- 节点间排斥、相关节点间弹簧连接，形成稳定布局；
- 悬停时降低无关路径透明度；
- 点击节点后，右侧 DOM 抽屉展示现有 `CareerPathView` 内容；
- 支持滚轮缩放、拖动画布和“回到当前岗位”。

### 数据可行性

现有接口已经返回 `promotion`、`lateral` 和 `transition`，并包含 `routes`、`nodes`、`stages`、`confidence`、`score/cap_similarity` 等字段，足以构造基础图谱。

当前问题是页面大量使用 `any`，缺少稳定图谱契约。实施前应增加：

```ts
interface CareerGraphNode {
  id: string
  title: string
  kind: 'current' | 'promotion' | 'lateral' | 'target'
  score?: number
  sampleCount?: number
  resourceDensity?: number
}

interface CareerGraphEdge {
  id: string
  source: string
  target: string
  kind: 'promotion' | 'lateral' | 'transition'
  confidence?: number
  capabilitySimilarity?: number
}
```

需要编写纯函数适配器，把不同接口格式统一为节点和边。Canvas 不应直接读取后端原始 `any` 对象。

### 技术实现

- 使用 p5 2D Canvas，不需要 WebGL；
- 采用轻量弹簧布局，不追求大型通用图数据库渲染器；
- 节点数量建议桌面端不超过 80，首版控制在 30–50；
- 物理布局稳定后降低帧率或调用 `noLoop()`；
- 仅在拖动、缩放、悬停或数据变化时重新启动绘制；
- 节点文字可用 Canvas 简短显示，完整信息必须放在 DOM 面板；
- 布局使用稳定随机种子，保证同一数据每次位置基本一致，便于用户记忆和视觉测试。

### 风险与边界

| 风险 | 处理方式 |
| --- | --- |
| 数据 ID 不稳定导致节点跳动 | 使用岗位 ID；缺失时以规范化标题和公司生成稳定键 |
| 节点过多导致混乱 | 默认只显示一到两层关系，支持按需展开 |
| 物理布局持续耗电 | 稳定后停止循环，只在交互时重绘 |
| Canvas 无法被读屏器理解 | 保留列表视图，并提供节点数量和当前选择的文本摘要 |
| 用户误以为距离代表严格数值 | 图例明确说明空间位置表示关系聚类，不是精确量尺 |

### 验收标准

- 30 个节点在普通笔记本上交互保持流畅；
- 首次稳定时间不超过约 1.5 秒；
- 点击节点能定位到对应列表/详情；
- 键盘用户可以通过列表完成全部操作；
- 减少动态效果模式直接显示稳定布局，不播放聚合运动；
- 图谱接口异常时自动回退到现有列表，不影响核心业务。

### 可行性结论

**高可行性、最高优先级。** 这是当前网站中最符合 p5.js 能力边界、也最能显著提升页面感染力的模块。

### 5.2 能力画像：材料证据汇聚动画

### 当前状态

画像页已有：

- 材料工作台；
- 材料来源、优势维度和待提升维度；
- 八维能力雷达；
- 完整度与竞争力；
- 行业适配和行动建议。

八维分数已经有明确类型 `CapabilityScores`，数据基础很好。当前主要问题不是缺少图表，而是用户无法直观看到“材料如何形成能力结论”。

### 推荐场景

在画像生成成功或材料重新分析完成后，播放一次 1.2–1.8 秒的证据汇聚动画：

1. 简历、证书、项目、竞赛和补充文本转化为不同形状的证据粒子；
2. 粒子根据材料种类和解析结果进入八个能力方向；
3. 每个维度的粒子数量表示证据数量；
4. 粒子亮度表示识别状态或置信度；
5. 八个能力节点依次点亮；
6. 动画结束后淡入现有 ECharts 雷达图。

后续新增单份材料时，不必重播全量动画，只让新增粒子进入受影响维度。

### 数据可行性

八维分数已经完备，但 `ProfileEvidenceMap.vue` 的材料仍以 `Record<string, unknown>[]` 传递，当前主要字段只有 `name`、`kind`、`status` 和 `chars`。如果后端没有“材料 → 维度贡献”关系，首版只能：

- 按材料类型生成粒子；
- 根据最终八维分数决定各方向的吸引强度；
- 明确说明这是生成过程的视觉概括，而不是逐条证据的精确归因。

如果希望实现真正可解释的证据动画，应扩展数据：

```ts
interface CapabilityEvidenceContribution {
  materialId: string
  dimension: CapabilityDimension
  weight: number
  confidence?: number
  excerpt?: string
}
```

### 技术实现

- Canvas 作为 `ProfileRadarCard` 上方或卡片内部的短时覆盖层；
- 动画完成后调用 `noLoop()`，不常驻运行；
- 粒子数量桌面端控制在 80–160，按材料数量采样；
- 使用吸引力场而非复杂碰撞；
- ECharts 雷达图保持原样，不使用 p5 重画；
- 当用户切换历史画像时，可以从旧八维节点平滑变形到新画像。

### 风险

- 如果没有真实维度贡献，动画可能被误解为精确证据流；
- 页面本身已有雷达图，动画时间过长会拖慢查看结果；
- 多次修改材料时频繁播放会造成疲劳。

处理方式：默认只在首次生成和明确点击“查看形成过程”时完整播放；小更新只播放局部脉冲。

### 验收标准

- 动画结束不阻塞雷达图和页面操作；
- 粒子颜色、形状具有图例；
- 页面离开可视区立即暂停；
- 生成失败时不播放成功汇聚；
- 静态模式显示“材料数量 → 八维分数”的 DOM 摘要。

### 可行性结论

**高可行性。** 数据成熟、实现边界清晰，适合在职业图谱基础设施之后实施。

### 5.3 人岗匹配：能力对齐与张力场

### 当前状态

匹配结果已经包含：

- 学生八维分数；
- 岗位八维要求；
- `match_score`；
- `dimension_gaps`；
- strengths、gaps、risks；
- 智能精排结果和粗排结果。

`MatchComparisonPanel.vue` 使用双雷达图精确对比，数据契约比职业图谱更成熟。

### 推荐场景

在岗位列表与雷达图之间增加一个短时“对齐场”：

- 左侧八个个人能力节点；
- 右侧八个岗位要求节点；
- 选择岗位时，两组节点向中央对齐；
- 个人能力达到要求时形成稳定绿色连接；
- 存在差距时形成暖色张力线，差距越大振幅越明显；
- 明显超出要求时产生向外扩散的优势光晕；
- 总体匹配度越高，结构越稳定；
- 切换岗位时保留个人节点，只让岗位节点和连接重新组织。

### 数据映射

| 数据 | 视觉映射 |
| --- | --- |
| 学生能力分数 | 左侧节点半径或亮度 |
| 岗位能力分数 | 右侧节点半径或目标环大小 |
| `dimension_gaps` | 连接颜色、张力和波动幅度 |
| `match_score` | 中央结构稳定度和总体光强 |
| strengths | 稳定绿色路径 |
| risks | 外围警示脉冲，不持续闪烁 |

### 集成方式

- 不替换 `DeferredCapabilityRadar`；
- 岗位卡点击后先更新 DOM 选中状态，再驱动 p5 场景；
- 动画控制在 450–800ms；
- 连续快速切换岗位时取消上一次插值，直接从当前状态过渡到最新目标；
- 画布默认不拦截指针，岗位选择仍由 DOM 完成；
- 可以提供“播放匹配解释”按钮，避免所有用户被强制观看。

### 风险

- 八条连接若同时抖动会显得焦虑；
- 用动画表达匹配分数可能造成过度权威感；
- 与雷达图重复表达会增加认知负担。

因此 p5 场景只用于解释“对齐过程”，精确分数、维度名称和差距仍由雷达图和文本承担。

### 验收标准

- 选择岗位后 100ms 内开始响应；
- 快速切换岗位不会堆积动画；
- 动画结果与 `dimension_gaps` 的正负方向一致；
- 不同色觉用户仍可通过线型、稳定度和 DOM 标签区分优势与差距；
- 场景失败不影响岗位选择和雷达图显示。

### 可行性结论

**高可行性。** 数据基础最好，适合作为第二批核心场景。

### 5.4 性格测试：生成式人格指纹

### 当前状态

性格测试结果目前包含 MBTI 类型、名称、摘要、四维解析、特征、工作偏好、成长建议和推荐岗位。`PersonalityHero.vue` 当前主要显示大号 MBTI 文字。

### 推荐场景

在结果 Hero 中生成一个可复现的“人格指纹”：

- 四个方向对应 E/I、S/N、T/F、J/P；
- 曲线对称性表示结构偏好；
- 粒子向内或向外的趋势表示能量方向；
- 分叉数量表示探索性；
- 线条稳定度表示决策确定性；
- 同一结果使用稳定随机种子，每次打开保持同一基础图案；
- 重新测试后旧图案平滑变形为新图案；
- 图案可用于结果分享卡片，但分享内容必须同时带文字类型和解释。

### 数据可行性限制

当前 `PersonalityDimensionAnalysis` 只有 `dimension`、`type`、描述和文本数组，没有数值化倾向比例。仅使用 MBTI 四个字母可以生成 16 种类型预设，但不能体现两个同为 INTJ 用户的差异。

首版可行方案：

- 使用 MBTI 字母决定结构；
- 使用回答序列生成稳定种子；
- 明确该图形是结果视觉签名，不代表精确心理测量。

更完整方案需要后端返回：

```ts
interface PersonalityDimensionScore {
  code: 'EI' | 'SN' | 'TF' | 'JP'
  left: number
  right: number
  confidence?: number
}
```

### 使用位置

- 推荐用于结果页，不推荐在答题过程中持续变化；
- 答题过程应保持安静，避免动态画面影响选择；
- 提交成功后可以用 800–1200ms 生成图案；
- 结果页面静止时只保留极轻微呼吸，不持续大幅运动。

### 风险

- 图形过于神秘会被误解为科学精确测量；
- 仅按 MBTI 类型生成会造成同类型图案雷同；
- 高动态背景会干扰长文本阅读。

### 验收标准

- 16 种类型具有可辨识但统一的视觉结构；
- 同一测试结果生成稳定；
- 结果摘要仍是页面主信息；
- 减少动态效果模式直接显示最终静态纹样；
- 导出分享时附带文本类型和免责声明。

### 可行性结论

**中高可行性。** 视觉回报高，但建议先扩展数值型维度数据，否则只能定位为品牌化结果签名。

### 5.5 生涯报告：路径生长、复盘脉冲与调整分叉

### 当前状态

报告模块已经具备目标岗位、能力差距、行动阶段、0–12 月发展线、复盘节点、计划调整和后台 AI 增强状态。现有 ECharts 折线图和 DOM 时间轴适合精确查看，不能被 Canvas 替换。

### 场景 A：报告生成状态

可以把普通加载反馈改为路径生长，但必须绑定真实状态：

| 真实状态 | p5 表现 |
| --- | --- |
| 请求已发出 | 起点出现、路径轻微呼吸 |
| 基础报告返回 | 主路径生长到目标岗位 |
| enrichment queued | 分支等待，节点缓慢排队脉冲 |
| enrichment running | 公开信息、叙事和推荐分支逐步点亮 |
| enrichment completed | 路径稳定，报告内容淡入 |
| enrichment failed | 主路径保留，增强分支变暗并显示重试入口 |

当前 `ReportEnrichmentStatus` 能表达 queued、running、completed 和 failed，但基础报告生成接口没有更细的服务端阶段。因此不得伪造“读取画像 20%、分析岗位 50%”等百分比。若要逐阶段展示，需要后端提供真实 stage 字段。

### 场景 B：发展路线概览

在报告概览增加非精确的“路线河流”视图：

- 每个目标岗位是一条发展流；
- 0–12 月是横向时间；
- 计划节点是菱形；
- 已复盘节点是圆形脉冲；
- 通过率决定路径亮度；
- 自动调整产生可见分叉，随后重新汇入未来月份；
- 点击节点联动现有 `ReportMonthlyTimeline` 和 `ReportMonthDetail`。

Canvas 用于总览和联动，ECharts 继续负责精确进度曲线。

### 场景 C：完成行动反馈

用户勾选下一步行动时，仅播放局部反馈：

- 当前行动粒子进入对应月份节点；
- 节点产生一次脉冲；
- 如果完成阶段里程碑，路径向前点亮一段；
- 不使用全屏庆祝，不打断继续工作。

### 数据可行性

`DevelopmentLine`、`DevelopmentLinePoint`、`DevelopmentAdjustment`、`ReportPlan` 和最新复盘数据已经足够驱动路线场景。主要需要建立规范化适配器，将缺失字段、字符串月份和不同调整结构统一为稳定场景模型。

### 风险

- 报告页信息密度已经很高，常驻动画会增加疲劳；
- Canvas 与 ECharts 同时运行可能增加 CPU 和内存；
- 打印/PDF 不应包含依赖实时 Canvas 的关键信息。

处理方式：只在概览或全屏模式启用 p5；滚出可视区立即 `noLoop()`；导出 PDF 使用现有 DOM/ECharts 或单独生成静态图。

### 验收标准

- Canvas 与时间轴选中月份双向同步；
- 调整分叉与真实 `DevelopmentAdjustment` 一一对应；
- 报告导出不依赖 Canvas；
- AI 增强失败时保留基础报告，不播放成功动画；
- 页面同时存在 ECharts 时总帧时间和内存仍在预算内。

### 可行性结论

**中高可行性。** 适合做局部、事件驱动的增强，不适合改造成持续运动的整页画布。

### 5.6 岗位探索：岗位星群模式

### 当前状态

岗位页具有分页列表、关键词筛选、岗位八维分数、平均分、公司、地点、薪资和助手筛选。列表适合搜索和比较，但不容易发现岗位之间的聚类关系。

### 推荐场景

在列表模式之外提供用户主动选择的“星群模式”：

- 每个岗位是一个节点；
- 行业或岗位族决定颜色；
- `score_avg` 或匹配分决定半径；
- 城市、薪资或八维能力相似性决定聚类；
- 搜索时相关节点靠近中心，无关节点向外围退散；
- 点击节点打开现有 `JobDetailModal`；
- 选中两个节点可显示能力距离；
- 提供列表/星群切换，不改变现有分页与筛选逻辑。

### 数据可行性

`JobCard` 已包含岗位 ID、标题、公司、地点、薪资和八维分数，可以计算能力空间距离。行业字段只在 `JobDetail` 中存在，如果希望按行业聚类，需要列表接口补充行业或在前端按标题建立弱分类。

当前分页可能只返回一页岗位。如果每页节点过少，星群价值有限；如果一次加载大量岗位，又会增加网络和渲染成本。建议首版仅使用当前筛选结果的 30–60 个节点，并明确“星群基于当前结果集”。

### 技术实现

- 使用网格近邻或简化碰撞，避免节点两两检测；
- 标签只显示悬停或选中节点；
- 缩放到远景时只显示颜色和大小；
- Canvas 交互区域与筛选表单分离；
- 小屏设备默认保留列表，不启用星群。

### 风险

- 空间位置可能被用户误解为系统排名；
- 节点标签拥挤；
- 同时加载过多岗位会影响性能；
- 行业字段不足会降低聚类解释力。

### 可行性结论

**中等可行性。** 适合作为高级探索模式，不应替代岗位列表，也不建议早于职业图谱实施。

### 5.7 全站工作流转场

### 当前状态

`CockpitStageRail` 已定义材料、画像、匹配、计划和复盘五个阶段，但页面之间主要依赖普通路由切换，阶段连续性仍以文字表达。

### 推荐场景

建立一个全局、共享、短时运行的路径转场层：

- 材料 → 画像：证据光点汇入八个方向；
- 画像 → 匹配：八个方向压缩成两组对齐节点；
- 匹配 → 计划：多个岗位路径收束为目标路线；
- 计划 → 复盘：路线节点形成月度脉冲；
- 反向返回时采用简化逆向动画，不强制完全倒放。

### 技术可行性

可以复用登录转场的 `document.body` 固定画布模式，但复杂度明显更高：

- 路由切换时旧页面和新页面的挂载时机必须协调；
- 需要保存来源页面的场景锚点；
- 新页面加载失败时必须能取消转场；
- 浏览器前进/后退不能出现状态错乱；
- 不能让每个页面创建独立全屏 Canvas。

建议只对用户点击 `CockpitStageRail` 的主动切换启用，不拦截所有 `NuxtLink`。

### 可行性结论

**中等可行性、较高工程风险。** 应在各页局部场景和共享宿主稳定后再实施。

### 5.8 首页：只做延迟加载的体验场景

### 当前状态

首页已有 Hero、流程板、模块入口、功能 Bento 和报告预览，信息层级完整。首页目前刻意不加载 p5 和 ECharts，这是构建预算的硬性检查项。

### 可行方案

不建议增加常驻粒子背景。可以在以下条件下使用 p5：

1. 用户点击“体验职业路径”按钮后加载；
2. `HomeExperienceShowcase` 接近视口并且浏览器空闲后预加载；
3. 场景位于独立模态框或局部区域；
4. 关闭体验后销毁实例；
5. 首页初始 HTML、Hero 图片和按钮完全不依赖 p5。

体验内容可以复用统一路径粒子系统，让用户拖动“材料、能力、岗位、计划”四类节点，看到一条职业路线如何形成。

### 不可接受方案

- 在 Hero 背景常驻全屏 p5；
- 首屏立即导入 p5；
- 用 Canvas 替换现有标题、图片或主按钮；
- 同时运行 p5、ECharts 和大图视频；
- 为视觉效果放宽首页 220 KB gzip 预算。

### 可行性结论

**技术上可行，性能上必须严格延迟。** 优先级较低。

### 5.9 明确不建议使用的页面

### 账户中心

账户、主题、推荐数量、AI 和隐私设置的目标是清晰、可信和快速。p5 会分散注意力，CSS 主题预览已经足够。

### 图谱后台管理

任务队列、质量覆盖率、发布配置、锁状态和错误处理属于运维界面。除极轻量的状态变化外，不应使用 Canvas 动效。

### 表格与正文

报告差距表、历史列表、岗位详情、行动清单和报告正文需要复制、搜索、读屏和打印，必须保留 DOM。

### 精确图表

八维雷达和发展折线已经由 ECharts 提供 Tooltip、坐标轴、图例和数据表回退。p5 不应重新实现这些能力，只能在图表前后表现生成或变化过程。

## 6. 推荐技术架构

### 6.1 共享宿主

建议新增统一宿主，而不是复制登录页代码：

```text
app/components/p5/
  P5SceneHost.client.vue        # 生命周期、画布、降级与状态
  P5SceneFallback.vue           # 静态摘要和错误回退

app/composables/p5/
  useP5SceneVisibility.ts       # IntersectionObserver / Page Visibility
  useP5ReducedMotion.ts         # 减少动态效果
  useP5Theme.ts                 # 主题色与 CSS 变量同步

app/utils/p5/
  math.ts                       # 插值、贝塞尔、向量
  seeded-random.ts              # 稳定随机种子
  particle-pool.ts              # 对象池，减少 GC
  scene-types.ts                # 场景接口

app/components/p5/scenes/
  career-graph/
  profile-evidence/
  match-alignment/
  personality-signature/
  report-routes/
  job-constellation/
```

场景接口建议：

```ts
export interface P5Scene<TData> {
  setup(context: SceneContext): void
  updateData(data: TData, options?: { animate?: boolean }): void
  draw(time: number): void
  resize(width: number, height: number): void
  setActive(active: boolean): void
  destroy(): void
}
```

页面只负责传递业务数据，不直接操作 p5 实例。

### 6.2 加载策略

- 使用 `<ClientOnly>` 或 `.client.vue`，避免 SSR/SSG 访问 `window`；
- 动态导入 `p5/core`；
- 场景接近可视区或用户主动打开时再加载；
- 同一路由只保留一个活跃实例；
- 全屏转场使用单独的全局实例；
- 页面离开或组件卸载时必须释放观察器、事件和画布；
- 不要把 p5 放进全局插件或 `app.vue` 的静态 import。

### 6.3 渲染策略

建议默认参数：

| 项目 | 建议值 |
| --- | --- |
| 渲染模式 | 2D Canvas |
| 像素密度 | 最大 1.25–1.35 |
| 活跃动画帧率 | 30–45 FPS |
| 静态场景 | `noLoop()`，事件触发重绘 |
| 桌面粒子量 | 80–240，按场景调整 |
| 移动端粒子量 | 桌面端的 30%–45% |
| resize | 防抖并重新计算布局 |
| 随机 | 稳定种子，禁止每次完全随机 |

只有职业图谱和岗位星群需要较长期交互循环；画像、匹配、报告反馈和人格生成都应是短时动画，结束后停止绘制。

### 6.4 业务事件契约

动画不应通过监听任意 DOM 变化猜测业务状态，应由业务组合式显式发送事件：

```ts
type VisualEvent =
  | { type: 'profile:generated'; scores: CapabilityScores; evidenceCount: number }
  | { type: 'match:selected'; student: CapabilityScores; job: JobCard; gaps: CapabilityScorePatch }
  | { type: 'report:enrichment'; status: ReportEnrichmentState }
  | { type: 'review:submitted'; month: number; passRate?: number }
  | { type: 'plan:adjusted'; adjustment: DevelopmentAdjustment }
```

事件必须来自真实成功状态。请求开始、请求失败和取消都应有明确处理。

## 7. 性能与稳定性要求

### 7.1 路由隔离

- 首页初始资源必须继续不包含 p5；
- 职业图谱首次进入时才允许加载 p5 核心；
- 画像和匹配页面只有在场景接近可视区或动画被触发时加载；
- 场景代码按路由拆分，但 p5 核心应由构建器复用，不重复打包。

### 7.2 CPU 与内存

- `document.hidden` 时调用 `noLoop()`；
- Canvas 离开可视区后暂停；
- 物理场景达到稳定阈值后停止；
- 使用粒子对象池，避免每帧创建大量对象；
- 不在 `draw()` 内查询 DOM、创建渐变缓存或重新解析业务数据；
- 文本测量和路径预计算应在数据更新时完成；
- 高核设备也不盲目使用高 DPR。

### 7.3 失败隔离

- p5 动态导入失败时显示静态组件；
- 场景异常不得阻塞页面数据加载；
- Canvas 永远不能覆盖核心按钮的点击区域；
- 交互场景应提供“关闭动画/切换列表”入口；
- 销毁逻辑需要幂等，避免路由快速切换时残留 Canvas。

## 8. 可访问性要求

每个 p5 场景都必须满足：

1. Canvas 标记为装饰时使用 `aria-hidden="true"`；
2. 承载信息时提供可关联的标题、文字摘要和 DOM 数据列表；
3. 所有关键操作可以通过键盘和 DOM 控件完成；
4. 不能只依赖颜色区分优势、差距和风险；
5. 支持 `prefers-reduced-motion: reduce`；
6. 减少动态模式显示最终稳定画面或完全使用静态替代；
7. 动画不得持续闪烁，不使用高频亮度变化；
8. Canvas 失败、暂停或被禁用时，业务信息不能丢失。

## 9. 测试策略

### 9.1 单元测试

- 后端数据到场景模型的适配器；
- 分数到颜色、半径、张力和位置的映射；
- 稳定随机种子；
- 空数据、缺失字段和异常分数归一化；
- 减少动态效果分支。

### 9.2 组件测试

- 动态导入失败时的静态回退；
- IntersectionObserver 进入和离开；
- 页面隐藏后暂停，恢复后继续；
- prop 更新不会重复创建实例；
- 卸载后 Canvas 和事件监听器被清理。

### 9.3 E2E 测试

- 职业图谱节点点击与详情联动；
- 匹配岗位快速切换只保留最新状态；
- 报告失败不播放完成动画；
- 路由前进/后退无残留 Canvas；
- 减少动态效果模式不运行长动画；
- 首页网络请求中不出现 p5 chunk，直到用户主动触发体验。

### 9.4 视觉测试

- 使用稳定数据和稳定随机种子截图；
- 覆盖亮色、暗色和主要主题色；
- 覆盖 1440px 桌面和低性能模拟；
- 对动态场景截取固定时间点，而不是比较随机帧；
- 允许微小抗锯齿差异，但不能忽略布局漂移。

### 9.5 性能测试

- 每阶段执行 bundle budget；
- 使用 Performance 面板检查长任务；
- 记录场景活跃和停止后的 CPU；
- 验证隐藏标签页帧率归零；
- 检查反复进出页面后 Canvas、监听器和内存是否增长。

## 10. 分阶段实施建议

### 阶段 0：共享基础设施

交付内容：

- `P5SceneHost.client.vue`；
- 场景生命周期接口；
- 可见性、主题和减少动态效果组合式；
- 稳定随机、粒子池和通用数学工具；
- 动态导入失败回退；
- 基础单元、组件和 E2E 测试；
- 新的 p5 路由资源预算规则。

退出条件：空白示例场景可以在任意业务页面安全挂载、暂停、恢复和销毁，首页未加载 p5。

### 阶段 1：职业图谱试点

交付内容：

- 图谱数据类型和适配器；
- 当前、晋升、横向和目标节点；
- 缩放、拖动、悬停、选中和列表联动；
- 稳定后自动停止；
- 图谱/列表切换和静态回退。

退出条件：真实数据下完成业务可用性、无障碍、性能和视觉验收。只有阶段 1 成功后才扩展其他页面。

### 阶段 2：画像与匹配

交付内容：

- 画像证据汇聚一次性动画；
- 岗位选择后的八维对齐动画；
- 与 ECharts 的显示节奏协调；
- 快速更新取消机制；
- 真实数据映射测试。

退出条件：动画能增加解释性，不延迟用户查看精确结果。

### 阶段 3：性格与报告

交付内容：

- 人格指纹静态和动态版本；
- 数值型性格维度接口评估；
- 报告真实状态路径；
- 复盘节点脉冲和调整分叉；
- 报告 Canvas 与 DOM 时间轴联动。

退出条件：不出现虚假进度，报告导出和长文本阅读不受影响。

### 阶段 4：可选增强

根据前几阶段真实用户反馈决定是否实施：

- 岗位星群模式；
- CockpitStageRail 跨页面转场；
- 首页用户主动触发的路径体验。

这些功能不能因为“视觉上好看”直接进入开发，必须有明确的使用场景和性能余量。

## 12. 最终建议

全站 p5.js 增强不应从“增加更多动画”出发，而应从“把职业规划过程变得可见”出发。

最合理的主线是：

1. 在职业图谱中把岗位关系变成可探索空间；
2. 在能力画像中让材料证据形成八维能力；
3. 在人岗匹配中让优势和差距产生可见张力；
4. 在生涯报告中让路线随着行动和复盘持续生长；
5. 用人格指纹和短时转场强化关键结果时刻。

应始终保留现有 DOM、ECharts、数据表和静态回退。p5.js 是业务信息的动态解释层，而不是页面内容层。只要坚持路由隔离、真实数据驱动、事件触发、动画结束即停止和可访问回退，这套技术可以显著增强 PathFy 的品牌辨识度，同时不破坏当前已经建立的性能与工程质量基线。
