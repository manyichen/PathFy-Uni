## 2. Phase 0 已完成内容

### 2.1 主目标正确性

- 后端强制校验 `primary_job_id` 必须属于 `target_job_ids`；
- 前端报告配置区支持显式“设为主目标”；
- 主目标随工作区缓存保存，不再依赖目标数组第一项；
- “下一次生成使用的主目标”和“当前报告快照主目标”分离，避免旧报告界面与旧基线不一致。

### 2.2 复盘真实性

- 复盘请求新增 `scope=target|all` 与 `job_id`；
- 默认复盘当前岗位，不再默认修改全部岗位；
- 指定岗位复盘只更新对应岗位计划、发展线和调整节点；
- 复盘记录持久化保存 `scope` 和 `job_id`；
- 前端明确展示本次复盘作用范围。

### 2.3 缺失数据处理

- 未提交指标的 `actual_value` 为 `null`，状态为 `missing`；
- 缺失指标不加入失败指标，也不再自动填为 0；
- 通过率仅基于实际有证据的指标计算；
- 指标不完整时复盘状态为 `insufficient`，保存记录但不自动重规划；
- 启发式和 LLM 提取均要求缺失字段返回/保留为空，不允许猜测低分；
- 前端显示“待补量化证据”或已评估项数，不再伪装为 0% 通过率。

### 2.4 并发与异步可靠性

- `career_reports` 新增 `report_version`；
- 行动勾选使用 compare-and-swap，冲突返回 409，不静默覆盖；
- 复盘记录与报告 JSON 在同一事务提交，并受版本约束；
- AI 增强的运行、完成、失败和合并均校验 `attempt`；
- 旧 attempt 被新任务替代后不能覆盖新结果；
- AI 合并继续保留用户行动进度和复盘产生的下月计划。

### 2.5 数据库与安全

- 删除报告仓储层的请求期 `CREATE TABLE`、`SHOW COLUMNS` 和 `ALTER TABLE`；
- 新增 Alembic 迁移 `20260819_0006_report_reliability.py`；
- 当前数据库已升级到 `20260819_0006`；
- 手工搜索和随机浏览要求登录；
- 两个发现接口增加进程内频率保护和 `Retry-After`；
- 报告路由的非预期异常不再向客户端暴露原始异常文本；
- 生产多实例部署仍应在 Nginx/API Gateway 增加聚合限流。

## 4. Phase 1 已完成内容

### 4.1 Career Report V2 决策结构

- 新增确定性 `decision_support` 适配层，旧报告无需迁移即可在读取时获得 V2 结构；
- 内容从长段落转换为“事实 → 结论 → 影响 → 行动 → 产物 → 验收指标”决策链；
- 每条结论携带事实引用、事实快照、优先级因子和证据质量等级；
- 每条行动携带产物、期限、投入、验收标准、所需证据和完成状态；
- 生成、历史读取、复盘重排和行动勾选后都会重建决策结构；
- V2 当前作为兼容结构附加在旧 JSON 上，未破坏历史报告字段和现有 PDF 导出。

### 4.2 页面信息架构

- 报告主体重组为“行动 / 依据 / 路线 / 复盘”四个可键盘操作的标签页；
- 默认打开行动页，只呈现一个主行动和最多两个辅助行动；
- 依据页集中展示判断、数据缺口、可展开证据、证据等级和新鲜度；
- 路线页合并发展路径、月份详情和阶段计划，不再同时渲染第二套重复时间线；
- 复盘页集中展示自动调整原因、复盘范围和提交入口；
- 标签、比较矩阵和证据卡均增加移动端布局，避免依赖横向表格浏览。

### 4.3 多目标决策

- 目标被区分为主目标、备选目标和观察目标；
- 新增岗位比较矩阵，展示匹配度、关键差距、优先行动和证据覆盖；
- 自动提取跨目标共享能力与共享行动，减少重复学习任务；
- 切换岗位时行动、证据、差距、岗位画像和路线使用同一 `job_id` 联动。

### 4.4 前端契约与交互

- 为 V2 决策结构补齐 TypeScript 类型和嵌套 Zod 校验；
- 非法证据等级、断裂的基本数据结构会在 API 边界被拒绝；
- V2 行动勾选继续复用 Phase 0 的乐观更新和冲突回滚机制；
- 旧报告没有 `decision_support` 时，行动区仍可从旧月度计划降级展示。

## 5. Phase 2 已完成内容

### 5.1 不可变输入与证据包

- 报告生成时冻结画像、岗位、目标角色、匹配目标、用户约束和配置版本；
- 输入快照使用规范化 JSON 计算 SHA-256，增强前重新校验，篡改或前后不一致时拒绝合并；
- AI 增强只读取冻结画像，不再重新读取可能已经变化的最新画像；
- 批量检索结束后生成独立证据包，记录目标事实、允许引用的资源和输入快照哈希；
- 历史报告没有快照时可基于其原始报告内容回填一次，后续继续校验同一哈希；
- 本阶段使用现有版本化 `report_json` 持久化，不需要新增数据库字段。

### 5.2 分层生成与结构化行动

- 增强链路明确划分为快照校验、批量证据检索、约束计划、结构化内容、叙事和质量门禁阶段；
- LLM 只能从 `allowed_fact_refs` 和候选资源 ID 中选择引用；
- 定制行动要求输出产物、日期、投入工时、验收规则、证据类型、关联维度、事实引用和资源引用；
- 未知事实引用和资源引用在合并前被过滤；
- Phase 1 的确定性决策适配器会优先使用这些结构化字段，同时继续兼容旧行动格式。

### 5.3 内容质量门禁

- 按事实可追溯 35、具体性 20、可执行性 20、覆盖完整 15、一致性 10 计算质量分；
- `>=85` 直接接受，低于 85 进行一次确定性局部修复，修复后仍低于 70 则回退规则版；
- 检查空泛行动、未知维度、非法行动类型、未知引用、重复行动、缺失里程碑、目标或匹配分变化；
- 检查跨岗位复制文案，并阻止“保证就业、确保入职、一定录用”等结果承诺；
- 修复只处理可确定字段，不让模型再次自由改写事实；
- 门禁状态为 `accepted / repaired / fallback`，前端显示状态和得分，不展示内部 Prompt 或模型异常。

### 5.4 异步进度与安全合并

- 异步状态新增 `scope`、`stage`、`progress` 和质量摘要；
- 前端展示快照校验、证据检索、计划生成、内容生成和门禁进度；
- 所有阶段更新继续受 attempt fencing 保护，旧任务不能写入新任务状态；
- 合并时先保留最新用户行动状态和复盘计划，再重建系统拥有的 V2 决策结构；
- AI 失败或门禁回退都不会删除规则版报告，也不会覆盖用户完成状态。

### 5.5 分区刷新

- 支持 `full`：完整增强；
- 支持 `narrative`：仅刷新文案；
- 支持 `resources`：仅刷新资源和资源关联计划；
- 支持 `plan`：仅重排计划；
- 前端依据工作区提供“仅刷新文案 / 仅刷新资源 / 仅重排计划”入口；
- 每种刷新范围都复用输入快照、证据包、质量门禁和版本合并规则。

## 6. Phase 3 已完成内容

### 6.1 两段式复盘事实确认

- 自然语言复盘先生成 `draft`，不会直接进入指标评估，也不会修改当前计划；
- 每个候选指标展示候选值、指标目标、原文或系统计算依据、来源类型和置信度；
- 候选值默认状态为 `pending`，用户可修改数值并选择“确认采用”或“忽略”；
- 只有明确确认的指标进入 `submitted_metrics`，未确认和被忽略项继续按缺失处理，不按 0 分处理；
- 旧 `review-cycle` 接口不再接受自然语言直通，只有显式结构化指标可走兼容确认流程；
- 前端流程拆分为“写原文 → 确认事实 → 决定计划提案”三步。

### 6.2 周复盘、月复盘与真实状态

- 复盘周期支持 `weekly / monthly`，前端模板随周期切换；
- 正式复盘状态支持 `on_track / partial / overloaded / evidence_missing / goal_changed / data_insufficient / stalled`；
- “目标改变、任务过载、推进停滞、证据缺失”作为真实情况优先于简单达标率；
- 没有确认指标时记录为 `data_insufficient`，不会增加连续失败次数；
- 指标只确认一部分时，仅对确认项评价，缺失项不进入失败指标。

### 6.3 计划提案与差异接受

- 复盘确认后，自动重规划只生成 `proposed` 版本，当前计划保持不变；
- diff 按目标岗位计划、共享成长计划和路线调整拆成可独立接受的变更；
- 岗位计划 diff 展示保留、新增、移除行动，以及计划月份、期限和投入信息；
- 用户可全部接受、部分接受、修改期限/投入后接受，或拒绝整份提案；
- 只有接受的变更会通过版本检查写回当前计划；拒绝不触碰当前计划；
- 提案生成后如果报告版本已变化，服务端返回 409，前端和历史列表标记为 stale/已过期。

### 6.4 版本、证据和审计记录

- 新增 `career_report_review_drafts`，保存原文、候选事实、提取元数据和确认状态；
- 新增 `career_report_plan_versions`，保存提案快照、结构化 diff、基线版本和接受/拒绝决定；
- 新增 `career_report_evidence_records`，保存用户确认的成果证据；
- 新增 `career_report_action_events`，记录复盘确认和计划提案接受/拒绝事件；
- 复盘确认、报告更新、提案创建、证据和事件在同一事务中提交；
- 历史区域只读展示计划提案状态、变更数量和过期状态。

### 6.5 数据库迁移

- 新增 Alembic 迁移 `20260819_0007_report_review_workflow.py`；
- Phase 3 完成时本地 MySQL 已升级到 `20260819_0007`，Phase 4 后当前 head 为 `20260819_0008`；
- schema doctor 已纳入四张 Phase 3 表和新 Alembic head 检查。

## 7. Phase 4 已完成内容

### 7.1 分层新鲜度与长期趋势

- 新增画像、岗位市场、资源、当前计划和正式复盘五类独立新鲜度，不再用一个报告更新时间代表全部数据；
- 当前画像晚于报告输入快照时，画像域直接标记为 `outdated`，提示重新分析画像并刷新报告；
- 每个域均返回数据日期、过期原因和明确刷新动作；
- 连续趋势只读取正式 `career_report_reviews`、已决定的计划版本和真实行动事件；
- 汇总复盘状态分布、目标变化次数、计划接受率、部分接受次数和计划稳定性；
- 最多展示最近 12 次正式复盘，未确认候选和复盘草稿不会进入趋势。

### 7.2 执行画像与保守个性化

- 执行画像区分样本不足、目标变化、时间容量不足、证据习惯不足、执行停滞、计划摩擦和稳定推进；
- 置信度由正式复盘与行动事件样本量决定，样本不足时明确显示低置信度；
- 个性化只调整建议的每周行动上限、投入时长和执行焦点，不直接改写用户计划；
- 低完成率、过载或反复重开行动时自动收缩任务数量，避免继续堆叠建议；
- 只有开启个人偏好、命中实验版本且至少存在 2 个有效样本时，个性化节奏才实际生效；
- 行动事件新增语义稳定引用，计划项目重排后不会仅凭数组下标关联长期历史。

### 7.3 提醒、界面与数据契约

- 行动工作区新增“长期校准”卡片，集中展示诊断、置信度、完成率、计划稳定性、建议节奏和证据样本；
- 展示五类数据的新鲜度以及对应刷新建议；
- 提供临近期限、行动逾期和复盘到期的站内提示；本阶段未接入短信、邮件或系统推送；
- 旧报告没有长期洞察字段时保持原页面，不出现空卡片；
- TypeScript 类型与 Zod 运行时契约完整覆盖长期洞察，非法状态或结构会在 API 边界被拒绝。

### 7.4 实验与运营指标

- 新增稳定哈希实验分组 `career_pacing_v1`，同一报告不会跨版本漂移；
- 支持 `baseline / personalized_v1`，关闭个性化偏好后建议不生效；
- 管理员运营接口提供草稿确认率、提案接受率、30 天活跃复盘人数和行动完成事件；
- 实验版本分别统计分配量、复盘激活率、提案接受率和每份报告行动完成事件；
- 指标均来自业务事件或正式记录，不以页面曝光或 AI 自述代替实际结果。

### 7.5 隐私、保留与数据库

- 账户设置新增“基于确认历史优化执行节奏”开关；
- 用户可从报告页导出该报告及目标、复盘、草稿、计划版本、证据、行动事件和实验分组的 JSON 数据；
- 后端提供需要再次确认报告编号的删除接口，删除后不可恢复，关联数据由外键级联清理；
- 未确认复盘草稿保留 90 天，并在创建新草稿时机会式清理；正式历史保留至用户删除报告；
- 新增 Alembic 迁移 `20260819_0008_report_longitudinal.py`；
- 新增 `career_report_experiment_assignments`，并为 `student_resume` 增加可用于快照失效判断的 `updated_at`。

### 7.6 本阶段明确未实施的可选项

- 导师/辅导员只读反馈和细粒度授权；
- 证据质量人工审核队列；
- 跨用户群体共性差距分析；
- 外部通知渠道与定时调度；
- 岗位市场数据定时采集任务。

这些能力涉及新的角色权限、人工运营流程或跨用户聚合隐私口径，不与个人长期校准核心闭环捆绑上线。

## 9. 最终收尾与上线交接

最终工程收尾已补充：

- 报告页“永久删除报告”入口，必须输入精确报告编号；
- 删除影响范围、不可恢复性和先导出提示；
- 导出与删除浏览器端到端用例；
- schema doctor 对报告级联外键和关键索引的强校验；
- E2E 与“行动 / 依据 / 路线 / 复盘”当前信息架构对齐；
- 按当前完整产物重建 bundle 发布基线并保留约 3% 余量。

预发布后按以下顺序推进：

1. 在测试或预发布环境执行 `alembic upgrade head` 与 schema doctor；
2. 先保持 `baseline` 与 `personalized_v1` 约 50/50 分组，至少积累 2 个正式样本后才解释个人节奏效果；
3. 以复盘激活率、行动完成事件/报告、计划接受率为主指标，同时监控删除率与重开率；
4. 校验数据导出内容和报告删除级联范围，不在生产环境用真实报告做删除冒烟；
5. 小流量运行一个完整周复盘周期后再调整节奏阈值，不根据单次行为提高任务量；
6. 只有在角色权限和授权范围确认后，再单独设计导师反馈与人工审核阶段。
