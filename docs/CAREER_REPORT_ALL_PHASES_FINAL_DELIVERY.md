## 1. 最终结论

本轮优化已经把生涯报告从“生成一份内容较长的 AI 报告”，升级为一个可持续使用的职业决策与执行工作台。最终模块具备以下闭环：

1. 用户明确选择主目标和备选目标；
2. 系统冻结输入快照并生成可立即使用的规则版报告；
3. AI 在证据包、候选资源和结构化契约内异步增强；
4. 质量门禁检查事实引用、具体性、可执行性、覆盖和一致性；
5. 用户围绕“行动、依据、路线、复盘”持续使用报告；
6. 自然语言复盘先变成候选事实，只有用户确认后才参与评估；
7. 重规划先生成差异提案，用户可以全部接受、部分接受、编辑或拒绝；
8. 长期校准只学习正式复盘、行动事件和计划决定；
9. 用户可以导出或永久删除报告及全部关联数据；
10. 管理员可以通过运营指标和稳定实验分组判断功能是否真正改善执行。

当前结论是“工程闭环完成，可以进入预发布和小流量验证”，不是“真实业务效果已经被证明”。代码正确性、契约、浏览器交互、迁移和运行时数据库结构已经验证；复盘留存、行动完成率提升等产品效果仍需真实用户周期数据验证。

## 2. 优化前的核心问题

### 2.1 用户体验与布局

- 页面同时展示摘要、计划、图表、复盘和推荐，缺少清晰阅读顺序；
- 用户首次进入后不容易判断“现在最应该做什么”；
- 多岗位内容并列但联动不完整，可能发生岗位、差距和计划错位；
- 路线图、月份计划和发展线表达重复；
- 失败状态、旧报告兼容和移动端操作不够明确。

### 2.2 内容可信度

- 长段落总结容易显得完整，但事实、判断和行动之间缺少明确引用关系；
- 缺失数据可能被错误解释为 0 或失败；
- AI 可能产生空泛动作、无依据资源或跨岗位复制文案；
- 报告生成期间画像或配置变化时，增强内容可能与最初输入不一致；
- “看起来合理”与“可验收、可复盘”没有被系统区分。

### 2.3 复盘真实性

- 自然语言中的数字如果直接被模型提取并参与评分，可能误读用户事实；
- 复盘作用范围不够明确，单岗位进展可能影响全部岗位计划；
- 未提交指标容易被当作失败；
- 自动重规划可能直接覆盖用户当前计划；
- 没有完整保存提案、接受/拒绝和证据历史。

### 2.4 工程可靠性

- 报告 JSON 并发写入可能覆盖行动状态；
- 异步 AI 的旧任务可能晚于新任务完成并覆盖新结果；
- 请求期数据库结构修补不适合生产部署；
- 缺少不可变输入哈希、质量门禁和安全回退；
- 缺少长期数据新鲜度、运营指标和用户数据权利闭环。

## 3. 优化目标与设计原则

本轮优化遵循以下原则：

- 正确性优先于文案丰富度；
- 规则版报告必须独立可用，AI 是增强而不是单点依赖；
- 事实、推断、建议和用户决定必须分层；
- 数据缺失必须显示为缺失，不能猜测为 0；
- AI 输出必须受结构、候选集合和证据引用约束；
- 用户确认是复盘事实进入长期历史的唯一入口；
- 重规划必须先提案、后决定，不能静默覆盖；
- 个性化只能在足够样本下保守生效；
- 所有长期建议必须能说明学习来源和排除项；
- 用户必须能够导出和永久删除自己的报告数据。

## 4. 优化前后对比

| 维度 | 优化前 | 优化后 |
|---|---|---|
| 首屏目标 | 展示一份完整报告 | 明确当前状态、主目标、最大差距和下一步 |
| 页面结构 | 多板块连续堆叠 | 行动、依据、路线、复盘四工作区 |
| 多目标 | 内容并列，联动有限 | 统一 `job_id` 联动目标、差距、行动、路线和公开信息 |
| 重要结论 | 主要是自然语言段落 | 事实 → 结论 → 影响 → 行动 → 产物 → 验收 |
| 缺失数据 | 容易与 0 或失败混淆 | `null / missing / data_insufficient` 明确区分 |
| AI 输入 | 可能读取变化后的最新数据 | 不可变快照、SHA-256 和证据包 |
| AI 输出 | 主要依赖 Prompt 约束 | 结构化字段、允许引用集合、质量评分和回退 |
| AI 失败 | 容易阻断完整报告 | 规则版始终保留，增强失败可重试 |
| 复盘 | 文本可能直接进入评价 | 草稿提取 → 用户确认 → 正式评价 |
| 重规划 | 可能直接修改计划 | proposed diff → 接受/部分接受/编辑/拒绝 |
| 并发 | 后写覆盖风险 | `report_version` compare-and-swap |
| 长期个性化 | 无明确数据边界 | 只用正式复盘、行动事件和计划决定 |
| 数据新鲜度 | 一个更新时间 | 画像、岗位、资源、计划、复盘五层状态 |
| 用户数据权利 | PDF 为主 | 完整 JSON 导出与强确认永久删除 |
| 运营评估 | 缺少闭环指标 | 分组激活率、接受率和行动完成事件 |

## 5. 最终系统工作流

```text
画像与岗位选择
    ↓
主目标/备选目标确认
    ↓
冻结输入快照 + 配置版本 + SHA-256
    ↓
确定性规则版报告立即返回
    ↓
异步 AI 增强
  ├─ 快照校验
  ├─ 批量证据检索
  ├─ 约束计划生成
  ├─ 结构化内容生成
  ├─ 叙事增强
  └─ 五维质量门禁
    ↓
安全合并并保留用户行动状态
    ↓
行动 / 依据 / 路线 / 复盘工作区
    ↓
自然语言复盘草稿
    ↓
用户逐项确认事实
    ↓
真实状态评估 + 计划差异提案
    ↓
用户接受、部分接受、编辑或拒绝
    ↓
正式历史、行动事件和长期校准
```

## 6. Phase 0：正确性与可靠性

### 6.1 主目标与多目标正确性

- 后端校验 `primary_job_id` 必须属于 `target_job_ids`；
- 前端允许显式设置主目标；
- 主目标随工作区缓存保存；
- 当前报告快照主目标与下一次生成配置分离；
- 岗位切换统一使用 `job_id` 驱动相关数据。

效果：避免目标数组排序变化造成主岗位漂移，也避免旧报告被新配置错误解释。

### 6.2 复盘作用域

- 复盘支持 `scope=target|all`；
- 单岗位复盘必须提供并校验 `job_id`；
- 默认围绕当前目标岗位复盘；
- 指定岗位复盘只更新对应岗位计划和路线调整；
- 正式复盘保存作用域和目标岗位。

效果：一个岗位的执行结果不会无条件修改其他目标的计划。

### 6.3 缺失数据语义

- 未提交指标保存为 `actual_value=null`；
- 缺失状态使用 `missing`；
- 缺失项不进入失败项；
- 通过率只基于实际有证据的指标；
- 信息不足时使用 `data_insufficient`，不增加连续失败次数；
- 前端展示“待补量化证据”，不展示伪造的 0%。

效果：报告不会因为用户没有填写某项数据而虚构失败结论。

### 6.4 并发与异步隔离

- `career_reports.report_version` 作为乐观锁版本；
- 行动勾选、复盘写入和提案接受使用 compare-and-swap；
- 冲突返回 409，前端回滚乐观状态并提示刷新；
- AI 增强使用 `attempt` fencing；
- 旧 attempt 不能覆盖新任务状态或结果；
- 合并时保留最新行动完成状态和正式复盘计划。

效果：降低用户刚勾选的行动被后台增强覆盖、旧任务覆盖新任务等真实数据损坏风险。

### 6.5 安全与迁移治理

- 报告发现相关接口统一要求登录；
- 随机浏览和搜索增加频率保护及 `Retry-After`；
- 非预期异常不再把内部异常文本返回客户端；
- 删除请求期 `CREATE TABLE / ALTER TABLE / SHOW COLUMNS`；
- 数据库结构统一通过 Alembic 管理；
- 新增迁移 `20260819_0006_report_reliability.py`。

## 7. Phase 1：内容模型与页面重构

### 7.1 Career Report V2 决策结构

新增 `decision_support.schema_version=2`，主要结构包括：

- `target_decisions`：每个目标岗位的推荐判断；
- `claims`：优势、差距、风险和机会；
- `facts`：结论引用的事实；
- `actions`：带产物、期限、投入和验收标准的行动；
- `target_comparison`：多目标对比；
- `shared_actions`：跨目标共享行动；
- `evidence_legend`：证据等级解释。

旧报告读取时由确定性适配器补充 V2 结构，无需一次性改写全部历史 JSON。

### 7.2 证据链

重要结论使用以下关系表达：

```text
事实引用 fact_refs
    ↓
结构化结论 claim
    ↓
对目标的影响 impact
    ↓
行动 action
    ↓
交付物 deliverable
    ↓
验收标准 acceptance_criteria
```

每条结论同时保存来源类型、证据等级、是否验证和新鲜度信息。

效果：用户可以判断建议来自系统计算、用户确认、公开事实还是较弱推断，而不是只能接受一段不可追溯文案。

### 7.3 四工作区布局

- 行动：默认入口，只突出一个主行动和最多两个辅助行动；
- 依据：判断、差距、证据、数据缺口和岗位公开信息；
- 路线：真实事件路径、月份详情和阶段计划；
- 复盘：复盘输入、事实确认、状态判断和计划提案。

效果：页面从“阅读报告”转向“今天行动、需要时查依据、按周期复盘”。

### 7.4 多目标比较

- 目标角色分为主目标、备选目标和观察目标；
- 比较矩阵展示匹配度、关键差距、主行动和证据覆盖；
- 识别共享能力与共享行动；
- 切换目标时计划、差距、路线和公开信息同步切换。

### 7.5 前端契约

- TypeScript 类型覆盖 V2 结构；
- Zod 对嵌套数据进行运行时校验；
- 非法证据等级和关键结构在 API 边界被拒绝；
- 历史报告缺少 V2 字段时保留降级展示。

## 8. Phase 2：AI 工作流与内容质量门禁

### 8.1 不可变输入快照

报告生成时冻结：

- 学生画像；
- 目标岗位；
- 主目标与备选关系；
- 匹配目标；
- 用户时间与计划约束；
- 系统设置 revision；
- 实际生效的配置快照。

规范化 JSON 计算 SHA-256。增强开始和合并前都会校验快照，AI 不重新读取可能已经变化的最新画像。

效果：同一次报告生成的规则版与 AI 增强版基于同一事实口径。

### 8.2 证据包与引用白名单

- 岗位信息批量检索，避免逐岗位重复调用；
- 生成独立证据包；
- LLM 只能选择 `allowed_fact_refs`；
- 推荐资源只能引用候选资源 ID；
- 未知事实引用和资源引用在合并前过滤；
- 旧报告可以基于原始报告内容回填一次快照。

### 8.3 结构化行动

行动至少包含：

- `kind`：learn / practice / deliverable；
- `title` 或 `text`；
- `deliverable`；
- `deadline`；
- `effort_hours`；
- `acceptance_criteria`；
- `evidence_required`；
- `evidence_type`；
- `source_fact_refs`；
- `resource_refs`。

效果：建议可以被勾选、交付和复盘，而不仅是“提升能力、加强实践”一类方向性表达。

### 8.4 五维质量门禁

| 维度 | 权重 |
|---|---:|
| 事实可追溯 | 35 |
| 具体性 | 20 |
| 可执行性 | 20 |
| 覆盖完整 | 15 |
| 一致性 | 10 |

处理规则：

- 总分不低于 85：接受；
- 低于 85：执行一次确定性局部修复；
- 修复后仍低于 70：回退规则版；
- 检查空泛行动、未知维度、非法类型、未知引用、重复行动和缺失里程碑；
- 检查目标、匹配分和输入快照一致性；
- 阻止保证就业、确保录用等结果承诺；
- 检查跨岗位复制文案。

门禁状态为 `accepted / repaired / fallback`，前端显示状态和得分，不暴露内部 Prompt 或异常细节。

### 8.5 异步进度与安全合并

- 阶段状态包含 `scope / stage / progress / quality`；
- 前端展示快照校验、证据检索、计划、文案和门禁进度；
- 所有写入继续受 attempt fencing 保护；
- AI 失败时保留规则版报告；
- 用户可以在 AI 运行期间继续查看和操作基础报告。

### 8.6 分区刷新

- `full`：完整增强；
- `narrative`：只刷新文案；
- `resources`：只刷新资源；
- `plan`：只重排计划。

所有刷新继续复用快照、证据包、门禁和版本保护。

## 9. Phase 3：真实复盘与计划版本

### 9.1 两段式复盘确认

自然语言复盘不会直接进入评分。流程为：

1. 保存原始复盘文本；
2. 提取候选指标；
3. 展示候选值、目标、原文依据、来源和置信度；
4. 用户修改、确认采用或忽略；
5. 只有明确确认的指标进入正式复盘；
6. 未确认和忽略项继续视为缺失。

旧 `review-cycle` 兼容接口只接受显式结构化指标，不再允许自然语言绕过确认流程。

效果：AI 负责整理候选，用户对事实最终负责。

### 9.2 周复盘、月复盘与真实状态

支持 `weekly / monthly`，正式状态包括：

- `on_track`：按计划推进；
- `partial`：部分完成；
- `overloaded`：任务过载或时间不足；
- `evidence_missing`：有行动但证据不足；
- `goal_changed`：目标发生变化；
- `data_insufficient`：数据不足；
- `stalled`：持续停滞。

目标变化、任务过载、停滞和证据缺失优先于简单达标率，更接近真实执行情况。

### 9.3 计划提案与差异决策

- 复盘后只生成 `proposed` 版本；
- 当前计划在用户决定前保持不变；
- diff 可拆分为岗位计划、共享成长和路线调整；
- 展示保留、新增和移除行动；
- 用户可全部接受、部分接受、编辑期限/投入后接受或拒绝；
- 提案基线版本变化时返回 409 并标记 stale；
- 拒绝不会触碰当前计划。

效果：自动重规划从不可见副作用变成可检查、可选择的用户决定。

### 9.4 审计数据

- `career_report_review_drafts`：复盘原文和候选事实；
- `career_report_plan_versions`：提案快照、diff 和决定；
- `career_report_evidence_records`：用户确认的成果证据；
- `career_report_action_events`：复盘、提案和行动事件；
- 复盘确认、证据、提案创建和报告版本更新在同一事务提交。

迁移文件：`20260819_0007_report_review_workflow.py`。

## 10. Phase 4：长期个性化与运营

### 10.1 分层新鲜度

| 数据域 | 作用 | 主要失效信号 |
|---|---|---|
| profile | 当前能力画像 | 画像晚于报告快照更新 |
| job_market | 岗位与匹配输入 | 快照超过岗位口径有效期 |
| resources | 学习与实践资源 | 增强结果长时间未刷新 |
| plan | 当前已接受计划 | 计划长时间未复盘或决定 |
| review | 最近正式复盘 | 超过复盘建议周期 |

每个域包含状态、数据日期、天数、原因和刷新动作。画像在报告快照之后变化时直接标记 `outdated`。

### 10.2 长期执行画像

只读取正式复盘和真实行动事件，诊断包括：

- `data_insufficient`；
- `goal_changed`；
- `time_capacity`；
- `evidence_habit`；
- `execution_stalled`；
- `plan_friction`；
- `stable`。

置信度由正式样本量决定。草稿和未确认候选不会增加置信度。

### 10.3 保守节奏建议

- 过载、停滞、低完成率或反复重开时，建议每周最多 2 项并降低投入；
- 节奏稳定且样本足够时，最多提高到 4 项；
- 其他情况保持中等节奏；
- 只给出行动上限、时间和焦点，不直接修改计划；
- 个性化开关开启、命中 `personalized_v1` 且至少有 2 个有效样本时才实际生效。

### 10.4 稳定行动引用

接口仍兼容使用岗位、计划项下标和行动下标定位当前页面操作，但长期事件新增 `action:v1:<hash>` 语义引用。哈希来自岗位、显式 ID、行动类型、标题和交付物，不依赖数组位置。

效果：计划重排后，长期事件不会只凭旧数组下标误认行动。

### 10.5 趋势和提醒

- 最近 12 次正式复盘序列；
- 状态分布；

## 24. 2026-08-19 可持续使用收尾

本轮针对真实使用中暴露的待办保存、AI 增强、历史报告和界面模板感进行了专项修复。

### 24.1 待办从展示卡片升级为可维护清单

- 为计划行动增加持久化 `action_uid`，完成状态不再依赖易变化的数组下标；
- 支持新增、编辑、删除、完成和重新打开；
- 用户编辑字段、用户新增行动、删除标记和完成时间在再次增强时继续保留；
- 增强产生的新交付物、期限和验收标准可以正常进入当月计划，不再被旧计划整块覆盖；
- 前端保存成功后保留即时反馈，新增/编辑/删除后重新读取服务器真值；
- 错误改为行动区内单条提示，避免重复全局弹窗。

### 24.2 AI 增强从多轮文案生成改为单轮有效行动生成

原流程包含资源策展、计划定制、分岗文案和总摘要等多次串行模型调用，且最终合并会覆盖增强计划。新流程调整为：

1. 使用岗位图谱和规则完成资源检索、排序和事实约束；
2. 仅调用一次模型，为当前阶段前两项关键缺口生成可验收行动；
3. 模型输出必须包含交付物、截止时间、投入小时、验收标准、证据类型和事实引用；
4. 全局摘要和分岗说明由已验证画像、岗位缺口、图谱资源及计划字段确定性生成；
5. 单次模型调用最长等待 45 秒，失败时保留规则计划，不阻塞报告使用。

这使外部模型调用由最多三次串行调用降为一次，并减少了跨三个阶段生成大量低利用率文案的输出负担。

### 24.3 增强状态与报告正文解耦

- 新增迁移 `20260819_0009` 和 `career_report_enrichment_jobs`；
- 排队、进度、错误、耗时和质量状态写入独立任务表；
- 长时间模型调用不再占用 `career_reports` 报告正文行锁；
- 最终增强结果只在合并瞬间短暂锁定报告；

## 25. 2026-08-19 依据工作区专项优化

本轮不只调整视觉，而是先修正依据链的判定口径，再以交互图和分层信息呈现真实状态。

### 25.1 发现并修复的流程问题

- 原能力区只读取扣除软容差后的 `dimension_gaps`。例如当前能力 70、岗位要求 78，原始差值为 8，但在 10 分软容差下会显示为 0，容易被误读成已经达标；
- 原决策模型只生成硬缺口与优势，没有表达“低于岗位要求、但尚未构成硬缺口”的风险；
- 原行动可能没有 `source_claim_ids` 和 `source_fact_refs`，但覆盖率只统计结论是否有事实，因此仍可能显示 100%；
- 原赛道画像把缺失值强制显示为 0，无法区分“真实低分”和“尚无数据”；
- 原资源区把推荐资源、竞赛入口和计划引用称为成果证据，容易把候选输入误认为已完成证明。

### 25.2 新的事实—结论—行动模型

后端现在同时保留三种能力状态：

1. `raw delta`：岗位要求减当前画像的原始差值；
2. `soft gap`：应用当前匹配策略容差后的有效硬缺口；
3. `risk claim`：原始差值大于 0、但处于软容差内的待验证项。

行动优先关联同一能力维度的硬缺口、待验证风险或优势结论；找到结论后，再继承对应事实引用。依据覆盖率改为四项加权：

- 结论事实化程度 35%；
- 行动可追溯程度 35%；
- 事实系统记录比例 20%；
- 输入完整度 10%。

同时返回结论数、事实数、行动数和断链行动数。覆盖率表示“链路完整程度”，前端明确提示它不等于录用概率或真实作品证明。

### 25.3 p5.js 决策依据板

首版“事实节点—结论节点—行动节点”关系图在真实报告中会出现重复数字、长行动截断和多条连线交叉，用户仍需自行推断每组事实属于哪个能力维度。二次优化已将其重构为按能力维度对齐的决策依据板：

- 每一行完整表达“能力维度—当前画像—岗位标尺—系统判断—关联行动—成果闭环”；
- 当前画像使用蓝色圆点，岗位要求使用紫色菱形，并直接标出高于或低于岗位标尺的真实差值；
- 硬缺口、容差内待验证、相对优势和发展机会使用不同状态色，不再用同一种紫色卡片表达所有结论；
- 行动列显示关联行动数、最近期限和下一项行动，不再堆放六个被截断的行动节点；
- 成果闭环明确区分“计划中、已勾选待复盘验真、已有 A 级成果、缺少行动”，勾选完成不会自动升级为真实证据；
- 无法映射到当前判断的行动单独显示为断链提示，不绘制误导性连线；
- 顶部将原“依据覆盖”更名为“链路完整度”，并独立展示 A 级成果数量；即使链路为 100 分、真实成果为 0，也会显示“链路已连通 · 成果待补”；
- 点击整行或下方能力索引可查看原始数值、判断摘要、交付物、期限和下一步补证任务；
- 大屏采用五列决策表，窄屏自动切换为纵向能力卡；
- 选中行只保留一条轻量状态流动效果，用于提示当前阅读路径，不再依赖装饰性粒子和曲线；
- 支持暗色模式、响应式尺寸、低性能设备像素比限制、不可见时暂停及减少动态效果偏好；
- p5.js 加载失败时保留可键盘操作的能力索引、数值详情与复盘入口，不影响报告使用。

该图不生成虚构节点，只消费服务端已有的事实、结论、行动和引用关系。
