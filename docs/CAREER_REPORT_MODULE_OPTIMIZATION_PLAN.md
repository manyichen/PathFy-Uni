# PathFy-Uni 生涯报告模块系统优化方案

> 文档状态：设计方案  
> 编写日期：2026-08-19  
> 适用范围：当前 Nuxt 4 前端与 Flask `domains/report` 后端  
> 目标版本：Career Report V2  
> 优先级口径：P0 为正确性与上线阻断，P1 为核心体验和可靠性，P2 为效率与精细化，P3 为长期能力

---

## 1. 文档目标

本方案不是简单调整生涯报告页面的颜色、卡片和文案，而是重新明确生涯报告在 PathFy-Uni 中的产品职责：

> 生涯报告不是一次性生成的长文本，而是一套以真实证据为基础、能够持续执行、复盘和修订的职业发展决策系统。

方案覆盖以下问题：

- 用户如何在较短时间内理解“我目前在哪里、为什么、下一步做什么”；
- 多目标岗位如何比较、如何设置主目标、如何避免计划相互冲突；
- 页面如何减少纵向堆叠、重复图表和认知负担；
- AI 如何生成有事实依据、可验证、不过度空泛的报告内容；
- 复盘如何区分系统事实、用户自述和 AI 推断，避免虚假量化；
- 自动重规划如何符合真实执行过程，并保留用户决策权；
- 报告生成、后台增强、行动更新和复盘并发时如何保证数据一致；
- 如何通过数据结构、API、质量门禁、测试和产品指标完成落地。

本方案基于当前代码而设计，保留已经有效的能力，包括：

- 最多 5 个目标岗位；
- 八维能力画像与岗位要求差距；
- 规则生成基础报告、AI 异步增强；
- 分岗位阶段计划、学习资源和竞赛推荐；
- 报告历史、行动勾选、月度复盘和计划调整；
- 0～12 月真实事件路径；
- PDF 导出、配置快照、隐私脱敏和用户归属校验。

## 2. 当前模块诊断

### 2.1 当前已经做对的部分

当前报告模块具备较完整的产品闭环：

```text
能力画像
  → 岗位目标
  → 能力差距与匹配
  → 基础报告
  → AI 增强
  → 行动执行
  → 月度复盘
  → 计划调整
```

其主要优势如下：

1. **规则与 AI 分层**：基础报告不依赖外部模型即可生成，模型失败时不会丢失整份报告。
2. **报告可持续演化**：报告、复盘、调整和行动状态均可保存，而不是一次性结果。
3. **多岗位独立计划**：每个目标岗位都有对应的差距、资源和阶段计划。
4. **可解释性基础较好**：页面已经展示匹配分、能力差距、赛道画像和评估指标。
5. **失败状态较完整**：AI 增强、历史记录、公开信息和 PDF 导出均有失败反馈与重试入口。
6. **真实事件可视化边界清晰**：报告路径只展示真实存在的起点、计划、复盘和调整事件，不用动画或前端计时伪造进展。

### 2.2 当前核心问题

| 问题 | 用户表现 | 深层原因 | 优先级 |
|---|---|---|---|
| 首屏之后页面过长 | 用户需要连续滚动，难以找到当前最重要任务 | 摘要、差距、时间轴、计划、证据、发展线和复盘按模块依次堆叠 | P1 |
| 信息存在重复 | “下一步”、下月计划、阶段计划、调整说明可能表达相近内容 | 缺少唯一的行动主视图和内容层级 | P1 |
| 主目标不透明 | 第一条目标自动成为主目标，但用户不能明确设置 | 前端没有主目标操作，后端也未强制校验 | P0 |
| 多目标复盘语义混合 | 一次复盘会调整所有岗位，但部分指标只按主目标计算 | 复盘没有 `scope` 和 `job_id` | P0 |
| 报告可能空泛 | AI 能给出“加强实践、持续复盘”等正确但无用的建议 | 内容生成缺少严格的证据引用、产物定义和质量门禁 | P1 |
| 复盘数字可能不真实 | 文本中没有数字时，模型或规则仍可能生成 0 或估算值 | “缺失”“未更新”“真实为 0”未被区分 | P0 |
| 自动调整缺少确认 | 复盘提交后计划直接变化，用户难以理解改了什么 | 缺少计划 diff、接受/编辑/拒绝流程 | P1 |
| 进步度容易被误解 | 发展线 0～100 可能被理解为真实能力分 | 当前数值是规则化执行进展，不是标准化能力测量 | P1 |
| 赛道指标新鲜度不足 | 用户看到 0～100 分，却难判断样本日期和覆盖范围 | 数据日期、样本量、数据源没有进入主要视觉层级 | P1 |
| AI 后台任务不够可靠 | 发布或进程退出时增强任务可能中断 | 任务在 Gunicorn 进程内线程池执行 | P0 |
| 报告写入存在覆盖风险 | AI 增强、复盘和行动勾选并发时可能互相覆盖 | 高频状态仍整体写回 `report_json` | P0 |
| 图谱查询开销偏大 | 多目标报告骨架生成仍可能较慢 | 赛道全图统计和资源检索存在重复查询 | P1 |

### 2.3 优化后的目标体验

用户进入报告页后，应在 10 秒内回答以下问题：

1. 我的主目标是什么，为什么选择它？
2. 我与目标之间最重要的 1～3 个差距是什么？
3. 这些判断分别来自什么事实，数据是什么时候更新的？
4. 本周或本月只需要优先完成什么？
5. 完成后需要留下什么可验证成果？
6. 当前计划是否因为复盘发生过变化，变化原因是什么？

系统不应要求用户先读完完整报告，才能找到下一步行动。

## 3. 产品设计原则

### 3.1 事实、判断、建议分层

报告中的内容必须明确属于以下哪一层：

| 层级 | 内容 | 例子 | 是否允许 AI 改写事实 |
|---|---|---|---|
| 事实层 | 已存储或可验证的数据 | 当前画像分数、岗位要求、完成的行动、作品链接 | 否 |
| 判断层 | 基于明确算法或规则的计算 | 匹配分、能力差距、优先级、达标判定 | 否，只能解释 |
| 建议层 | 基于事实和判断生成的行动策略 | 下月项目、课程、练习、复盘方式 | 可以，但必须受约束 |
| 表达层 | 面向用户的总结和叙事 | 为什么先补实践、为什么暂缓冲刺 | 可以 |

AI 的职责主要位于建议层和表达层，不能凭空修改事实层和判断层。

### 3.2 每个结论都要回答“依据是什么”

任何重要结论至少关联一个 `evidence_id`：

- “实践技能是最大差距”应关联学生画像快照、岗位要求快照和差距计算版本；
- “建议完成 SQL 项目”应关联岗位能力要求、对应差距和资源条目；
- “计划完成率 60%”应关联本周期可执行行动数与已完成行动事件；
- “岗位贴合度提高 3 分”应关联相同岗位快照和两次画像版本。

如果缺少证据，应显示“当前证据不足”，而不是用流畅文案掩盖数据不足。

### 3.3 每个行动都必须可验收

“学习 Python”“提升沟通能力”“多参加实践”不应直接成为计划项。一个有效行动至少包含：

- `action`：要做什么；
- `deliverable`：留下什么产物；
- `deadline`：何时完成；
- `effort`：预计投入；
- `acceptance_rule`：什么情况算完成；
- `evidence_type`：用什么证据证明；
- `linked_gap`：它对应哪个能力差距；
- `source_refs`：建议依据与资源来源。

示例：

```text
行动：完成一个公开数据集的 SQL 分析专题
产物：GitHub 仓库 + 1 页业务结论 + 5 分钟讲解视频
截止：本月第 4 周
投入：每周 3 小时
完成标准：不少于 8 个查询、包含 2 个窗口函数、结论经一次同伴反馈
证据：仓库链接、报告文件、反馈截图
对应差距：实践技能、岗位表达
```

### 3.4 缺失数据不能等同于零分

系统必须区分：

- `measured`：系统真实测量或计算；
- `self_reported`：用户自述并确认；
- `inferred`：AI 从文本中提取，尚未确认；
- `not_updated`：本周期没有足够新数据；
- `not_applicable`：当前目标不适用。

任何复盘指标都不能把 `not_updated` 自动转成 `0`，否则会错误触发强化重规划。

### 3.5 AI 失败不阻断执行

无论外部 AI、公开检索还是图谱推荐是否可用，系统都应至少提供：

- 能力差距；
- 主目标与备选目标；
- 规则化的近期行动；
- 行动完成记录；
- 结构化复盘；
- 历史报告恢复。

## 4. 用户旅程优化

### 4.1 首次生成报告

```text
选择画像
  → 导入或选择目标岗位
  → 明确设置主目标
  → 确认可投入时间和计划周期
  → 生成事实骨架
  → 立即进入“本月行动”
  → AI 分区增强并逐段更新
```

首次生成前增加一个轻量约束步骤：

| 输入 | 建议形式 | 作用 |
|---|---|---|
| 每周可投入时间 | 2 / 5 / 8 / 12+ 小时 | 控制任务数量与复杂度 |
| 目标周期 | 3 / 6 / 12 个月 | 控制阶段规划 |
| 当前阶段 | 探索 / 准备实习 / 求职 / 转方向 | 调整行动优先级 |
| 优先成果类型 | 项目 / 证书 / 竞赛 / 实习 / 社交验证 | 影响证据路径 |
| 目标风险偏好 | 稳妥 / 平衡 / 冲刺 | 替代当前只有 `fit/stretch` 的粗粒度表达 |

这些约束比让 AI自由猜测用户节奏更可靠。

### 4.2 日常返回报告

回访用户不应再次看到完整报告配置，而应直接看到：

1. 本周最重要行动；
2. 截止时间和完成证据；
3. 当前阻塞项；
4. 最近一次计划变化；
5. 距离下次复盘的时间。

推荐默认入口为“行动工作台”，完整报告放在次级标签中。

### 4.3 月度复盘

```text
系统汇总本月真实事件
  → 用户确认行动与证据
  → 用户填写阻塞和主观感受
  → AI 提取候选指标
  → 用户确认或修改指标
  → 系统规则评估
  → 生成计划调整草案
  → 用户查看差异并接受、编辑或拒绝
```

复盘不再是“输入一段话后系统直接重写计划”。

### 4.4 目标变化

真实职业规划允许目标变化，因此增加以下操作：

- 设为主目标；
- 降为观察目标；
- 暂停目标；
- 替换目标并保留旧目标历史；
- 记录变更原因：兴趣变化、机会变化、能力反馈、时间约束、外部建议等。

目标变化应生成真实时间线事件，但不能修改过去报告快照。

## 5. 信息架构与页面布局

### 5.1 总体信息架构

将当前超长单页重组为“固定摘要 + 四个工作区标签”：

```text
报告页
├─ 固定页头：主目标、报告版本、数据新鲜度、AI 状态、导出/历史
├─ 决策摘要：状态、差距、下一步、风险
├─ 标签 1：行动
│  ├─ 本周/本月最佳行动
│  ├─ 待办、阻塞、即将到期
│  └─ 当前阶段计划
├─ 标签 2：依据
│  ├─ 能力差距
│  ├─ 匹配解释
│  ├─ 岗位与赛道证据
│  └─ 数据来源与新鲜度
├─ 标签 3：路线
│  ├─ 0～12 月真实状态路径
│  ├─ 阶段里程碑
│  └─ 计划调整记录
└─ 标签 4：复盘
   ├─ 快速周检
   ├─ 月度复盘向导
   ├─ 历史复盘
   └─ 计划版本差异
```

### 5.2 桌面布局

建议采用三列工作台，但只有中间主内容滚动：

```text
┌──────────────────────────────────────────────────────────────┐
│ 页头：主目标 / 版本 / 新鲜度 / AI 状态 / 历史 / 导出         │
├──────────────┬──────────────────────────────┬────────────────┤
│ 目标轨道      │ 主内容                        │ 行动侧栏        │
│              │                              │                │
│ ● 主目标      │ [行动][依据][路线][复盘]      │ 下一步行动      │
│ ○ 备选目标    │                              │ 截止时间        │
│ ○ 观察目标    │ 当前标签内容                  │ 需要的证据      │
│              │                              │ 阻塞与提醒      │
│ + 添加目标    │                              │                │
└──────────────┴──────────────────────────────┴────────────────┘
```

布局规则：

- 左栏宽度约 220～260px，只负责目标切换、主目标和状态；
- 中栏最小宽度 640px，承载主要内容；
- 右栏宽度约 280～320px，保持下一步行动持续可见；
- 低于 1180px 时右栏折叠为顶部行动卡；
- 低于 768px 时目标轨道改为下拉选择器。

### 5.3 首屏内容

首屏保留四个问题，但增强真实性：

| 卡片 | 内容 | 必须显示 |
|---|---|---|
| 当前状态 | 当前计划月、最近一次有效活动 | 时间、数据来源 |
| 主目标 | 岗位、公司/岗位类别、目标策略 | 可切换“设为主目标” |
| 首要差距 | 当前值、岗位要求、差值 | 置信度和更新时间 |
| 下一步 | 一个最优先行动 | 截止时间、产物、完成标准 |

避免使用“暂无明显差距”作为笼统结论。若证据不足，应显示“当前画像证据不足，建议先补充材料”。

### 5.4 减少重复可视化

当前报告同时存在真实状态路径、13 个月时间轴、月份详情和发展线图。优化后：

- 保留 p5.js 真实状态路径作为路线主视图；
- 月份详情作为路径节点的详情抽屉或下方面板；
- ECharts 发展线只在“复盘趋势”中显示，并明确它是“执行进展指数”；
- 删除重复表达相同月份状态的独立长时间轴，或改成路径的无障碍 DOM 镜像；
- 提供“图形 / 表格”切换，保证可访问性和可导出性。

### 5.5 移动端布局

移动端遵循“一个屏幕只处理一个决定”：

1. 顶部目标选择器；
2. 当前行动卡；
3. 四标签横向滚动导航；
4. 内容单列展示；
5. 底部固定“更新行动 / 开始复盘”主按钮；
6. 复杂差距表默认只显示前三项，其余展开；
7. 计划 diff 使用逐项卡片，不使用宽表格。

## 6. 报告内容模型优化

### 6.1 从“段落报告”转为“决策单元”

报告内容的最小单元不再是一段文字，而是：

```text
事实 Fact
  → 结论 Claim
  → 影响 Impact
  → 行动 Action
  → 产物 Deliverable
  → 验收 Metric
```

示例：

```json
{
  "claim": "实践技能是当前首要补齐项",
  "fact_refs": ["profile:v12:cap_req_practice", "job:job-1:v8:cap_req_practice"],
  "facts": {
    "student_score": 62,
    "job_requirement": 78,
    "gap": 16,
    "confidence": 0.84
  },
  "impact": "该岗位要求能够独立完成从数据处理到业务结论的交付闭环",
  "action_ref": "action-203",
  "quality": {
    "grounded": true,
    "freshness": "2026-08-18",
    "source_type": "system_calculated"
  }
}
```

### 6.2 报告结构

每个目标岗位的报告应包含以下结构：

#### A. 目标判断

- 推荐定位：主目标 / 备选 / 观察；
- 当前匹配分及计算版本；
- 适合该目标的 2 个主要理由；
- 需要谨慎的 1～2 个风险；
- 数据不足项。

#### B. 优势证据

最多展示 3 项，每项必须包含：

- 能力维度；
- 学生当前表现；
- 支撑材料或计算依据；
- 对岗位的实际价值；
- 证据等级。

#### C. 关键差距

最多展示 3 项，按“影响 × 可改善性 × 紧迫度”排序，而不是只按差值排序。

建议优先级公式：

```text
priority = gap_size × job_importance × confidence × improvability × urgency
```

其中：

- `gap_size`：学生与岗位的有效差距；
- `job_importance`：该维度对目标岗位的重要程度；
- `confidence`：学生画像与岗位要求置信度；
- `improvability`：在当前计划周期内可改善程度；
- `urgency`：实习、投递或目标日期带来的时间约束。

#### D. 近期行动

- 只突出 1 个主行动；
- 最多 2 个辅助行动；
- 每项都定义产物、截止日期和验收方式；
- 每月总投入不得超过用户可投入时间的 80%，保留缓冲。

#### E. 3/6/12 月阶段路线

- 3 个月：补基础和形成第一个可验证成果；
- 6 个月：形成岗位化作品或真实协作经历；
- 12 个月：形成稳定投递、实习或职业迁移能力；
- 若用户只选择 3 或 6 个月周期，不强行生成 12 个月详细任务。

#### F. 备选策略

- 如果主目标不可行，哪个备选目标复用最多已有能力；
- 哪些行动对多个目标共同有效；
- 哪些行动只服务单一目标，应谨慎投入。

### 6.3 证据等级

| 等级 | 定义 | 示例 | 可用于客观达标 |
|---|---|---|---|
| A | 可直接验证的外部或上传成果 | 仓库、证书、作品、比赛结果、正式反馈 | 是 |
| B | 系统内结构化事件 | 行动完成记录、画像重新计算、测评结果 | 是，但需看事件质量 |
| C | 用户自述并确认 | “本月完成两次讲解” | 有限使用 |
| D | AI 推断但未确认 | 从自由文本推断“完成率约 70%” | 否 |

用户界面统一显示来源标签：

- 系统计算；
- 用户确认；
- 已验证成果；
- AI 待确认；
- 数据不足。

### 6.4 数据新鲜度

每个主要板块显示独立新鲜度：

- 画像：最近一次材料更新时间；
- 岗位要求：岗位快照时间和评分版本；
- 招聘热度：数据样本日期、样本数量和覆盖岗位数；
- 图谱资源：图谱 revision；
- AI 内容：模型、生成时间和所依据的报告版本；
- 公开信息：搜索时间、搜索提供方和缓存状态。

禁止只显示“86 分招聘可见度”而不显示样本边界。

## 7. AI 生成工作流优化

### 7.1 总体原则

AI 不直接面对原始数据库对象自由写报告，而是接收经过规则层整理的“证据包”。

```text
数据快照
  → 事实标准化
  → 规则计算
  → 证据检索
  → 约束生成
  → 程序校验
  → 必要时修复
  → 版本化入库
```

### 7.2 阶段 0：冻结输入快照

生成报告时冻结：

- `profile_snapshot_id`；
- `profile_scoring_version`；
- `job_snapshot_id` 与岗位能力版本；
- `graph_revision`；
- `settings_revision`；
- 用户时间、周期、风险偏好等约束；
- 主目标与备选目标关系。

同一报告版本的所有判断必须基于同一组快照，避免生成过程中数据变化导致前后矛盾。

### 7.3 阶段 1：确定性事实骨架

由程序生成，不调用 LLM：

- 目标岗位基本信息；
- 八维学生值、岗位要求值、差值和置信度；
- 匹配分及算法版本；
- 优势和差距候选；
- 图谱路径与资源候选；
- 当前行动预算；
- 数据缺失和风险标记；
- 规则化起步行动。

这部分应在短时间内返回并可立即使用。

### 7.4 阶段 2：批量证据检索

所有目标一次完成：

- 批量解析 `JobTitle`；
- 一次获取全部目标的赛道统计；
- 一次批量获取课程、竞赛、晋升和横向路径；
- 对资源执行 URL、更新时间、重复项和岗位相关性过滤；
- 公共资源与分岗位资源分别标记。

避免按 5 个目标重复执行全图统计。

### 7.5 阶段 3：约束规划器

先由程序完成任务组合，不让 LLM 决定所有任务：

1. 根据差距优先级选择最多 3 个本期重点；
2. 根据每周可投入时间计算最大行动数；
3. 优先选择能产生 A/B 级证据的行动；
4. 多目标时优先选择共享价值高的行动；
5. 检查资源、时间和前置依赖；
6. 生成结构化行动草案。

LLM 只负责把草案个性化、补充合理细节和改善表达。

### 7.6 阶段 4：LLM 结构化生成

按目标批量生成，输出严格 JSON：

```json
{
  "job_id": "job-1",
  "summary": {
    "decision": "string",
    "reasons": [
      {"text": "string", "fact_refs": ["string"]}
    ],
    "risks": [
      {"text": "string", "fact_refs": ["string"], "mitigation": "string"}
    ]
  },
  "actions": [
    {
      "action_id": "string",
      "title": "string",
      "deliverable": "string",
      "deadline": "YYYY-MM-DD",
      "effort_hours": 8,
      "acceptance_rule": "string",
      "evidence_type": "project|certificate|feedback|event|other",
      "linked_dimensions": ["cap_req_practice"],
      "fact_refs": ["string"],
      "resource_refs": ["string"]
    }
  ]
}
```

模型约束：

- 不能引用证据包外的课程、竞赛、岗位数字和 URL；
- 不能把缺失值写成 0；
- 不能承诺就业结果；
- 不能使用“持续提升、全面加强、积极参与”等无产物动词作为完整行动；
- 每条关键建议必须包含 `fact_refs`；
- 任务总工时不得超过输入预算；
- 不得输出无法由当前用户完成或无法验收的任务。

### 7.7 阶段 5：内容质量门禁

程序对 AI 输出计算质量分：

| 维度 | 权重 | 检查方式 |
|---|---:|---|
| 事实可追溯 | 35 | 所有 `fact_refs` 是否存在，数字是否一致 |
| 具体性 | 20 | 是否包含产物、截止、投入、完成标准 |
| 可执行性 | 20 | 工时是否合理、是否存在前置依赖冲突 |
| 覆盖完整 | 15 | 是否覆盖结论、风险、行动和阶段目标 |
| 一致性 | 10 | 主目标、差距、计划和摘要是否相互一致 |

门禁建议：

- 总分 `>= 85`：直接接受；
- `70～84`：程序修补可确定字段，并标记低置信内容；
- `< 70`：最多进行一次定向修复调用；
- 修复后仍不达标：保留规则版内容，不展示低质量 AI 文案。

同时检查：

- 资源 URL 必须存在于检索候选集合；
- 事实数字必须与证据包一致；
- 同一岗位行动不能高度重复；
- 多岗位建议不能只是替换岗位名称；
- 不展示模型原始错误和内部 Prompt。

### 7.8 阶段 6：异步任务与版本合并

建议将进程内线程池迁移为持久化队列：

```text
career_ai_jobs
  id
  report_id
  report_version
  job_type
  attempt
  idempotency_key
  status
  lease_owner
  lease_expires_at
  progress
  result_version
  error_code
```

更新必须带条件：

```sql
UPDATE career_ai_jobs
SET status = 'completed'
WHERE id = ? AND attempt = ? AND status = 'running';
```

旧 attempt 不得覆盖新 attempt。AI 结果按字段所有权合并：

- AI 可更新：叙事、建议理由、定制行动和资源排序；
- 用户拥有：行动完成状态、复盘原文、已接受计划、目标状态；
- 系统拥有：匹配分、差距、指标判定、版本信息；
- 已经发生的历史事件任何模块都不能覆盖。

### 7.9 分区刷新

避免“重新生成整份报告”覆盖用户状态。提供：

- 刷新岗位公开信息；
- 重新推荐学习资源；
- 重新生成当前岗位文案；
- 基于新画像重算差距；
- 基于新约束重排近期行动；
- 创建完整新版本。

每种操作显示影响范围。

## 8. 防止报告内容空泛的具体规则

### 8.1 禁止单独出现的表达

以下表达如果没有后续产物和标准，不构成有效建议：

- 持续提升综合能力；
- 加强实践；
- 多参加项目；
- 提升沟通能力；
- 关注行业趋势；
- 定期复盘；
- 不断积累经验；
- 建立个人品牌。

### 8.2 建议最小合格条件

每条行动至少满足 5 项中的 4 项：

- 有明确对象；
- 有明确数量；
- 有明确产物；
- 有明确期限；
- 有明确验收人或验收规则。

每个岗位计划至少满足：

- 2 条量化岗位事实；
- 2 条学生事实；
- 1 条主要优势；
- 1 条关键风险；
- 1 个当前主行动；
- 1 个可验证成果；
- 1 条备选路径或失败应对。

### 8.3 数据不足时的正确输出

错误做法：

```text
你的社会网络能力较弱，建议多参加行业活动。
```

正确做法：

```text
当前画像中“社会实践网络”的材料证据较少，暂不能判断真实水平。
本月先补充一次行业交流或导师访谈记录；完成后再决定是否将该维度列为主要差距。
```

### 8.4 个性化差异检查

对同一用户的不同目标岗位，至少满足一项显著差异：

- 首要差距不同；
- 行动产物不同；
- 资源不同；
- 风险不同；
- 阶段重点不同。

如果不同岗位生成内容相似度超过阈值，应回退为规则解释或触发一次定向修复。

## 9. 复盘机制优化

### 9.1 两级复盘

#### 快速周检：2 分钟

只收集真实执行状态：

- 本周计划行动完成了哪些；
- 新增了哪些成果或证据；
- 当前最大阻塞是什么；
- 下周可投入时间是否变化；
- 是否需要暂停某项任务。

快速周检不重新计算完整匹配分，也不自动大幅改计划。

#### 月度复盘：5～8 分钟

包含：

- 本月行动完成情况；
- 成果证据确认；
- 新增材料是否触发画像更新；
- 主目标意愿是否变化；
- 时间、资源和阻塞变化；
- 系统指标确认；
- 下月计划调整。

### 9.2 复盘作用域

新增 `scope`：

```text
global               整体执行节奏、时间和共同能力
target:job-1          单一目标岗位
targets:[job-1,job-2] 多个指定目标
```

规则：

- 全局复盘只能调整共享行动和时间预算；
- 单岗位复盘只能调整该岗位计划；
- 主目标差距变化不得自动用于其他岗位；
- 用户切换主目标时创建目标变更事件，而不是改写旧记录。

### 9.3 指标重新设计

#### A. 系统可直接计算

| 指标 | 计算方式 | 注意事项 |
|---|---|---|
| 行动完成率 | 已完成的到期行动 / 本期应完成行动 | 暂停或取消行动不进入分母 |
| 按时完成率 | 截止前完成行动 / 已完成行动 | 无截止日期不参与 |
| 证据产出 | 新增 A/B/C 级证据加权和 | 不只统计数量 |
| 执行连续性 | 本期有有效活动的周数 / 周数 | 不把频繁点击当成有效活动 |
| 计划负载 | 实际投入 / 用户可投入时间 | 用于判断计划是否过载 |

#### B. 有条件才能计算

| 指标 | 前提 | 无前提时 |
|---|---|---|
| 能力短板缩小 | 有新材料并重新生成画像 | `not_updated` |
| 岗位贴合度变化 | 同一岗位快照口径 + 新画像版本 | `not_updated` |
| 赛道机会变化 | 有更新后的同口径市场数据 | `not_updated` |

#### C. 主观指标

- 目标意愿 1～5；
- 任务难度感受 1～5；
- 时间压力 1～5；
- 自我效能 1～5；
- 对计划的认可度 1～5。

主观指标用于调整计划负载，不能直接替代能力事实。

### 9.4 自然语言提取改为“草稿确认”

当前流程可从文本直接产生指标。优化后：

1. AI 从文本提取候选事实；
2. 每项显示原文依据；
3. 用户确认、修改或删除；
4. 未确认项保留为 `inferred`，不参与客观达标；
5. 确认后才生成正式评估。

示例：

```text
AI 候选：本月完成 2 次项目讲解
原文依据：“和同学做了两次五分钟演示”
[确认 2 次] [修改] [不计入]
```

### 9.5 复盘评价不应只有“通过/失败”

建议状态：

- `on_track`：按计划推进；
- `partial`：完成部分，有明确阻塞；
- `overloaded`：计划负载超过实际时间；
- `evidence_missing`：可能完成但缺少成果证据；
- `goal_changed`：目标偏好发生变化；
- `data_insufficient`：数据不足，不能评估；
- `stalled`：连续多个周期无有效行动。

不同状态对应不同策略，不能全部归入“未达标”。

### 9.6 重规划规则

| 状态 | 调整方式 |
|---|---|
| on_track | 保持节奏，仅滚动下月任务 |
| partial | 减少并行任务，保留最重要行动 |
| overloaded | 降低计划负载，延长截止时间 |
| evidence_missing | 不新增学习任务，优先补成果证明 |
| goal_changed | 暂停自动调整，进入目标重新确认 |
| data_insufficient | 请求补数据，不惩罚、不累计失败 |
| stalled | 分析阻塞原因，必要时拆小任务或建议人工咨询 |

只有在相同作用域下连续两次真实 `partial/stalled`，且不是数据缺失或过载，才进入强化调整。

### 9.7 计划差异与用户确认

重规划生成后先进入 `proposed` 状态，展示：

- 保留了什么；
- 删除了什么；
- 新增了什么；
- 截止时间如何变化；
- 为什么调整；
- 预计投入如何变化；
- 对哪个目标生效。

用户可以：

- 接受全部；
- 接受部分；
- 编辑后接受；
- 拒绝并保留原计划。

只有接受后的版本进入当前计划。历史计划和历史行动完成状态保持只读。

## 10. 多目标岗位优化

### 10.1 目标角色

最多 5 个目标可以保留，但角色必须明确：

- 1 个主目标；
- 最多 2 个备选目标；
- 其余为观察目标。

只有主目标默认生成完整行动计划。备选目标生成差异化简版计划；观察目标只展示依据和差距，避免 5 套计划同时执行。

### 10.2 目标对比

增加多目标决策矩阵：

| 比较项 | 主目标 | 备选 A | 备选 B |
|---|---:|---:|---:|
| 匹配分 |  |  |  |
| 高置信差距数 |  |  |  |
| 可复用能力 |  |  |  |
| 预计补齐周期 |  |  |  |
| 资源覆盖 |  |  |  |
| 当前意愿 |  |  |  |
| 数据新鲜度 |  |  |  |

矩阵不替用户作最终决定，而是说明权衡。

### 10.3 共享行动

计划项新增：

```json
{
  "shared_target_ids": ["job-1", "job-2"],
  "reuse_score": 0.82
}
```

优先推荐可同时支持多个目标的成果，例如：

- 数据分析作品可能同时服务数据分析师与商业分析师；
- 通用沟通训练可服务多个岗位；
- 高度特定的证书或工具只服务单一岗位时要显示机会成本。

## 11. 前端交互状态设计

### 11.1 报告状态机

```text
empty
  → configuring
  → generating_skeleton
  → skeleton_ready
  → enriching
  → ready
  → stale
  → updating
```

异常状态独立存在：

- `skeleton_failed`；
- `enrichment_partial`；
- `enrichment_failed`；
- `graph_unavailable`；
- `public_info_unavailable`；
- `export_failed`；
- `version_conflict`。

### 11.2 生成过程反馈

不要使用虚假的百分比进度。展示真实阶段：

```text
✓ 已读取能力画像
✓ 已加载 3 个目标岗位
✓ 已计算能力差距
✓ 基础行动计划可用
● 正在补充分岗位建议
○ 正在校验资源和内容
```

每个目标岗位可独立显示增强状态，某个目标失败不阻断其他目标。

### 11.3 版本与新鲜度提示

以下情况报告进入 `stale`：

- 用户生成了新画像；
- 岗位能力版本更新；
- 图谱 revision 更新；
- 用户更改主目标或时间预算；
- 报告超过设定有效期。

提示用户选择：

- 仅查看旧报告；
- 重算差距；
- 创建新版本；
- 查看版本变化。

不自动覆盖历史报告。

### 11.4 编辑能力

用户应能编辑：

- 主目标和目标角色；
- 截止日期；
- 每周时间预算；
- 行动标题和产物；
- 行动暂停/取消原因；
- AI 提取的复盘事实；
- 重规划草案。

用户不能直接编辑系统计算值，但可以发起“数据不准确”反馈并查看来源。

## 12. 数据模型与 API 优化

### 12.1 数据模型演进原则

不建议一次性重写现有 `report_json`。采用两阶段演进：

#### 阶段 A：V2 JSON + 乐观锁

在 `career_reports` 增加：

- `schema_version`；
- `content_version`；
- `profile_snapshot_id`；
- `graph_revision`；
- `status`；
- `primary_job_id` 强校验；
- `updated_by_event_id`。

所有写入使用：

```sql
UPDATE career_reports
SET report_json = ?, content_version = content_version + 1
WHERE id = ? AND user_id = ? AND content_version = ?;
```

受影响行数为 0 时返回 `409 version_conflict`，前端重新加载并提示用户。

#### 阶段 B：拆分高频写入数据

新增或强化：

| 表 | 职责 |
|---|---|
| `career_report_versions` | 不可变报告快照 |
| `career_report_targets` | 目标角色、状态、目标快照 |
| `career_plan_items` | 当前行动与阶段计划 |
| `career_plan_events` | 完成、暂停、编辑、取消事件 |
| `career_evidence_items` | 成果证据和验证状态 |
| `career_review_cycles` | 周检/月度复盘、作用域、状态 |
| `career_review_metrics` | 指标值、来源、置信度和缺失状态 |
| `career_plan_revisions` | 重规划草案、diff、接受状态 |
| `career_ai_jobs` | 持久化 AI 任务 |

`report_json` 继续作为读取优化后的聚合快照，而不是唯一事实来源。

### 12.2 建议 API

#### 报告与目标

```text
POST   /api/report/generate
GET    /api/report/{id}
GET    /api/report/{id}/versions
POST   /api/report/{id}/versions
PATCH  /api/report/{id}/targets/{job_id}
POST   /api/report/{id}/targets/{job_id}/make-primary
POST   /api/report/{id}/refresh-gap
```

#### AI 任务

```text
POST   /api/report/{id}/ai-jobs
GET    /api/report/{id}/ai-jobs/{job_id}
POST   /api/report/{id}/ai-jobs/{job_id}/retry
```

请求中明确 `job_type`：

- `full_enrichment`；
- `target_narrative`；
- `recommendation_refresh`；
- `plan_personalization`；
- `public_info_summary`。

#### 行动与证据

```text
PATCH  /api/report/{id}/actions/{action_id}
POST   /api/report/{id}/actions/{action_id}/events
POST   /api/report/{id}/evidence
PATCH  /api/report/{id}/evidence/{evidence_id}
```

行动使用稳定 `action_id`，不再依赖 `item_index/action_index`。索引在重规划后可能变化，不能作为长期标识。

#### 复盘与重规划

```text
POST   /api/report/{id}/reviews/prepare
PATCH  /api/report/{id}/reviews/{review_id}/draft
POST   /api/report/{id}/reviews/{review_id}/confirm
GET    /api/report/{id}/reviews/{review_id}/replan
POST   /api/report/{id}/replans/{replan_id}/accept
POST   /api/report/{id}/replans/{replan_id}/reject
```

`prepare` 只生成待确认事实，不立即写入正式指标和当前计划。

### 12.3 API 错误约定

后端返回稳定错误码，不向前端暴露原始数据库或模型异常：

```json
{
  "ok": false,
  "code": "REPORT_VERSION_CONFLICT",
  "message": "报告已在其他操作中更新，请重新加载后继续",
  "request_id": "req_xxx",
  "retryable": true
}
```

建议错误码：

- `REPORT_PROFILE_MISSING`；
- `REPORT_TARGET_INVALID`；
- `REPORT_PRIMARY_TARGET_INVALID`；
- `REPORT_GRAPH_UNAVAILABLE`；
- `REPORT_VERSION_CONFLICT`；
- `REPORT_AI_JOB_STALE`；
- `REPORT_REVIEW_NEEDS_CONFIRMATION`；
- `REPORT_DATA_INSUFFICIENT`；
- `REPORT_EXPORT_UNAVAILABLE`。

## 13. 后端可靠性、性能与安全

### 13.1 移除请求期 DDL

当前仓储层的运行时建表和补列逻辑应迁移至 Alembic。应用账号在生产环境只保留 DML 权限。

启动阶段执行只读 schema 检查：

- 缺表或缺列时健康检查报告 `degraded`；
- 关键迁移缺失时拒绝启动报告写入能力；
- 不在第一个用户请求中执行 `ALTER TABLE`。

### 13.2 图谱查询优化

- 赛道统计按 `graph_revision` 缓存；
- 对多个 JobTitle 使用一次 `UNWIND`；
- 课程与竞赛批量检索；
- 随机浏览改为数据库分页，不缓存 32 份完整岗位列表；
- 对搜索和随机浏览增加鉴权、限流和最大页数；
- 将生成耗时分解为 profile、jobs、gap、track、relations、recommendations、persist。

建议基础报告性能目标：

| 指标 | 目标 |
|---|---:|
| P50 | < 1.5 秒 |
| P95 | < 4 秒 |
| P99 | < 8 秒 |
| 单次 Neo4j 往返 | 目标数为 5 时不超过 5 次 |

### 13.3 PDF 导出

当前按请求启动 Chromium，内存开销高。优化方案：

- 独立导出任务队列；
- 同一报告版本复用已生成 PDF；
- 以 `report_id + version + locale` 作为缓存键；
- 导出页面只使用静态 HTML/CSS，不访问外部资源；
- 部署检查必须确认 Chromium 真正安装，构建过程不吞掉失败；
- 前端展示“准备中”，完成后提供下载通知。

### 13.4 安全与隐私

- 报告目标搜索、随机浏览和公开信息接口增加鉴权与限流；
- 后端日志记录完整异常，前端只接收稳定错误码；
- 复盘原文继续默认脱敏存储；
- 本地缓存不保存完整复盘原文和个人姓名，优先只缓存 `report_id`、当前目标和必要展示快照；
- 外部检索返回的 URL 必须和原始搜索候选逐项匹配；
- AI 输出不得包含联系人、用户身份或未提供的个人事实；
- 保留用户关闭外部 AI 的能力，关闭后使用规则版报告。

## 17. 分阶段实施路线

### Phase 0：正确性与可靠性，P0

目标：保证报告不会错误评估、错误覆盖或错误重规划。

工作项：

- 强制校验主目标属于目标集合；
- 前端增加“设为主目标”；
- 复盘增加 `scope/job_id`；
- 缺失指标改为显式状态，不再默认 0；
- 复盘与行动更新增加乐观锁或事务；
- AI 任务增加 attempt 条件更新；
- 移除原始异常向前端暴露；
- 搜索和随机浏览增加鉴权、限流；
- 禁止请求期 DDL，部署统一走 Alembic；
- 增加上述回归测试。

验收：

- 并发更新不丢行动和复盘；
- 单岗位复盘不会修改其他岗位；
- 数据不足不会被判为失败；
- 旧 AI 任务不能覆盖新任务；
- schema doctor 和全量测试通过。

### Phase 1：报告内容与页面重组，P1

目标：让报告更短、更可信、更能执行。

工作项：

- 页面改为行动/依据/路线/复盘四标签；
- 增加目标轨道和主目标角色；
- 合并重复时间线表达；
- 引入事实—结论—行动—验收内容单元；
- 行动增加产物、期限、投入和完成标准；
- 增加证据等级和数据新鲜度；
- 实现多目标比较矩阵；
- 完整化前端 Zod Schema；
- 清理未使用组件和 `any`。

验收：

- 用户在首屏能明确看到一个主行动和完成标准；
- 所有关键结论可展开查看依据；
- 页面默认不再形成超长模块堆叠；
- 移动端无横向溢出；
- 每条行动均可验收。

### Phase 2：AI 工作流与内容门禁，P1/P2

目标：减少空泛内容和幻觉，提高分岗位差异。

工作项：

- 建立冻结快照和证据包；
- 批量图谱检索；
- 约束规划器；
- 严格 JSON 输出；
- 事实引用、URL、工时和重复度校验；
- 内容质量评分和一次定向修复；
- 分区刷新；
- AI 任务持久化 worker。

验收：

- 关键结论事实引用覆盖率 100%；
- AI 不得生成候选集合外 URL；
- 行动工时不超过用户预算；
- 低质量输出可靠回退到规则版；
- 不同岗位的行动具有真实差异。

### Phase 3：真实复盘与计划版本，P1/P2

目标：使复盘能准确反映执行，而不是由模型替用户编数字。

工作项：

- 周检和月度复盘分离；
- AI 提取草稿确认；
- 行动事件和证据表；
- 有条件指标与缺失状态；
- 复盘状态分类；
- 重规划草案、diff 与接受流程；
- 报告版本与 stale 提示。

验收：

- 未确认 AI 指标不参与评估；
- 无新画像时贴合度显示“未更新”；
- 重规划不会静默覆盖当前计划；
- 用户可部分接受或拒绝调整；
- 历史计划可回放。

### Phase 4：运营、导师与长期个性化，P3

可选工作项：

- 复盘提醒和逾期提醒；
- 导师/辅导员只读反馈；

- 群体共性差距分析；

- 基于历史接受/拒绝行为改进建议排序；
- 岗位市场数据定期更新与口径管理。

## 20. 最终目标

优化完成后的生涯报告应具备以下特征：

1. **可信**：事实、计算、用户自述和 AI 推断彼此分离；
2. **具体**：每个行动都有产物、期限、投入和完成标准；
3. **聚焦**：用户随时只看到最重要的下一步，而不是被长报告淹没；
4. **真实**：缺少数据时承认不知道，不把未更新当成失败；
5. **可控**：AI 提取需要确认，计划调整需要接受；
6. **可追溯**：结论有证据、计划有版本、变化有原因；
7. **可持续**：周检负责保持节奏，月度复盘负责校准方向；
8. **可靠**：任务中断可恢复，并发操作不丢失用户数据；
9. **可衡量**：成功标准从“生成了一份报告”升级为“执行并形成了可验证成果”。

一句话概括目标形态：

> PathFy-Uni 生涯报告 V2 应从“AI 帮用户写规划”升级为“系统用事实帮助用户做决定、执行行动并校准路径”。
